## 3. 원가 구조 — 우리가 실제로 계산할 수 있는 숫자

이 과제의 변동비는 **LLM 호출 비용이 대부분**이라고 가정합니다. (가정: 지금 구성처럼 SQLite 를 로컬 PC 에서 돌릴 때. Supabase·클라우드 호스팅을 쓰면 그 요금이 더해집니다 [확인 필요: 요금제·사용량])

원가는 **민원 수에 비례하는 몫**(①분류)과 **시간에 비례하는 몫**(②감시·④통합은 민원 수와 상관없이 주기마다 돎), **요청서 수에 비례하는 몫**(③조치)으로 나눠 계산합니다.

```
축제 1회 원가  C = N × (1 − h) × a  +  K × b  +  D × d

  N  민원 건수                     (아래 표의 가정 1,000건)
  h  분류 캐시 적중률               〔 〕
  a  분류 1건 원가                  CLI 참고 $0.01328   ※
  K  실제로 돈 배후 주기 수          운영 시간(분) 〔 〕 ÷ 주기(기본 1분) × (1 − ④ 건너뜀 비율 〔 〕)
  b  배후 1주기(②감시 + ④통합) 원가  CLI 참고 $0.1878    ※ ($0.0930 + $0.0948)
  D  조치요청서 건수                〔 〕
  d  요청서 1건 원가                CLI 참고 $0.0877    ※ ($0.1753 ÷ 2건)
  원화 환산                          × 환율 〔 〕원/$ (기준일 〔 〕)

  ※ 출처: 원가측정_참고.md (2026-09-30 15:31) — Claude Code CLI 경유 참고값 · 합성 시드 · 1주기 1회 측정.
    API 직접 호출과 금액이 다르므로 제출용 값은 `--backend anthropic` 실측으로 바꿉니다.
```

> ⚠ 원가측정_참고의 **"민원 1건당 $0.08590"에 민원 수를 곱해 원가를 계산하면 안 됩니다.** 그 값은 한 주기 전체 비용($0.4295)을 그 주기에 분류한 5건으로 나눈 것이라, 민원이 많으면 내려가고 적으면 올라갑니다.
>
> **읽을 점:** 배후 1주기가 약 $0.19(CLI 참고)라, 1분 주기로 오래 돌리면 배후 몫이 분류 몫보다 커질 수 있습니다. 원가를 좌우하는 것은 민원 수보다 **배후 주기 간격과 ④ 건너뜀 장치**(카드 구성이 그대로면 호출하지 않음)이고, 이 둘은 설정으로 조정할 수 있습니다.

| 항목 | 값 | 비고 |
|---|---|---|
| 민원 1건당 평균 토큰 | 〔 〕 | API 실측(`measure_cost`)으로 채움. <sub>CLI 참고: 분류만 5건 평균 입력 843 · 출력 304 · 캐시 읽기 2,332 (원가측정_참고의 합계를 5로 나눈 값)</sub> |
| 민원 1건 원가 | 〔 〕원 | a × 환율. <sub>API 측정 전에는 CLI 참고 a = $0.01328 에 'API 미측정'을 붙여 씀</sub> |
| 분류 캐시 적중률 | 〔 〕% | 측정 전. <sub>실제 리뷰(D6-6) 리플레이로 측정. 합성 시드는 반복 문장이 많아 적중률이 부풀려지므로 쓰지 않음</sub> |
| 축제 1회(민원 1,000건 가정) 원가 | 〔 〕원 | 위 식 C. <sub>지금 계산할 수 있는 것은 분류 몫뿐: 1,000 × $0.01328 = $13.28 (캐시 0 가정 · CLI 참고). 배후 몫은 운영 시간·건너뜀 비율, 요청서 몫은 요청서 수가 있어야 계산</sub> |

**제안 단가의 논리.** 하한 = 원가 C + 초기 설정(작업 시간 × 공표 단가) + 운영 지원 〔 〕 / 상한 = 사람으로 할 때의 비용 또는 비슷한 공공 계약가. 두 쪽 모두 근거가 있을 때만 범위로 쓰고, 한쪽만 있으면 그쪽만 씁니다. 마진·할인율은 근거가 없어 〔 〕로 둡니다.

> **측정 방법**: `core/db.py`의 `agent_log`에 호출별 지연시간과 토큰 수가 이미 남습니다(원가측정_참고가 그 기록으로 만든 표).
> API 키로 `measure_cost` 를 돌려 a·b·d 를 에이전트별로 따로 찍으면, 발표에서 **"민원 1건 분류 원가 ○원 + 배후 1주기 ○원"**을 숫자로 말할 수 있습니다.
> 이 숫자가 있으면 비즈니스 모델 10점에서 다른 팀과 확실히 갈립니다.

## 4. 시장과 확장 경로

```
1단계  축제 1개 (진주남강유등축제)          ← 대회 제출 범위
   ↓   구역·부서 매핑만 교체
2단계  경남 시군 축제로 수평 확장
   ↓   분류 라벨 교체
3단계  지자체 상시 민원 (도로·환경·소음)
   ↓   
4단계  대학 축제, 체육대회, 박람회 등 대규모 행사 일반
```

**확장이 싼 이유**: 구역·부서 매핑·분류 라벨을 **설정 데이터로 분리**했기 때문입니다
(`core/config.py`의 `ZONES` / `DEPARTMENT_MAP` / `LABELS`). 코드 수정 없이 교체됩니다.
발표 때 **다른 축제 설정으로 바꿔 실행하는 장면**을 넣으면 확장성 주장이 말이 아니라 증거가 됩니다.

> 경남 시군 수와 연간 축제 개최 건수는 **문화체육관광부 축제 통계 또는 각 시군 공고**에서
> 확인한 뒤 인용하세요. 확인 못 하면 "경남 18개 시군" 정도로만 쓰고 건수는 빼세요.

## 5. 사회적 가치 (수익 외)

- **안전 사고 예방** — 건수에 묻히던 안전 민원이 3건에서 드러난다. 사고 1건을 막으면 금전 가치를 넘어선다
- **행정 신뢰** — 방문객이 제기한 민원이 실제 조치로 연결되는 경로가 생긴다
- **데이터 축적** — 축제별 민원 이력이 쌓이면 다음 해 기획 단계의 근거가 된다

## 6. 경쟁·대체재 대비

| 대체재 | 한계 | 우리의 차이 |
|---|---|---|
| 현장 민원 접수대 | 인력 필요, 기록이 안 남음 | QR 무인 접수, 전건 기록 |
| 국민신문고 | 처리 기간이 축제 기간(3~10일) 안에 끝나기 어려움 [확인 필요: 출처 — 민원처리법상 처리기간 등 공식 근거] | 접수 즉시 관제 유입 표시, 분류는 수십 초 안(CLI 경유 약 20초, API 미측정) |
| 리뷰 감성분석 솔루션 | 사후 집계, 건수 순 정렬 | **실시간 + 심각도 순 + 부서별 문서 생성** |
| 일반 챗봇 | 답변만 함 | **판단하고 문서를 만들어 부서로 넘김** |
