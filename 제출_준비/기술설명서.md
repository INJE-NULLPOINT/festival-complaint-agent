| 항목 | 기재 내용 |
|---|---|
| 팀명 / 부문 / 주제 | 철철철 / 대학부 / ⑤ 경남 지역혁신·공공서비스 AI Agent |
| 작품명 | 실시간 축제 민원 관제 AI Agent (대상: 진주남강유등축제) |
| 해결 문제 | 건수 순으로 보면 적게 들어오는 안전 민원(어두운 길·난간·밀림)이 많은 불편 민원(주차·가격)에 묻혀 대응이 늦어진다 |
| 대상사용자 | 축제 운영 담당 주무관·현장 운영요원(관제·조치 화면), 방문객(QR 접수) |
| Agent Goal | 민원을 분류하고 심각도로 순위를 매겨 "지금 조치할 일"과 담당 부서 조치요청서를 만든다 |
| 사용 AI/LLM/모델 | Claude Opus 5.5(`claude-opus-5-5`), Claude Code CLI(`claude -p`) 경유. 심각도 점수는 결정적 함수(`severity.ts`)가 계산 |
| 사용 Tool/API/Data/장비 | 도구: get_pending·save_classification·lookup_similar(분류), get_window_stats·score_label·raise_alert·save_snapshot(감시), write_request·get_department·collect_quotes·generate_doc·lookup_festival_info(조치), rank_issues·rank_actions·write_briefing·read_agent_results(통합), plan_cycle(계획). Data: 개발용 합성 시드 160건(실제 리뷰 아님), 축제 정보 수기 시드(TourAPI 미사용), 이태원 공개 112 녹취 11건(재현 시험용). DB: Supabase Postgres / SQLite, 문서: DOCX |
| Memory/State/Feedback 구현 | - State: 민원·분류·카드·조치 상태·실행 기록(`agent_log`)을 DB에 유지 / - Memory: 비슷한 과거 민원을 찾아 분류에 참고(`lookup_similar`), 운영자가 정한 유형을 먼저 씀 / - Feedback: 운영자의 조치 상태 변경이 다음 판정에 반영(S-06 미조치 30분 ×1.2), 운영자가 지정한 '확인 필요' 민원은 다음 분류의 기억 |
| 핵심 Workflow (End-to-End) | ① 방문객이 QR 화면에서 민원을 쓴다 / ② 워커가 개인정보를 가린 뒤 저장하고 접수 원문은 지운다 / ③ ①분류 에이전트가 유형·안전 여부를 정한다(신뢰도 0.3 미만은 '확인 필요') / ④ ⓪계획이 이번 주기 단계를 정하고, ②감시가 심각도 함수를 도구로 호출해 등급을 매긴다 / ⑤ ③조치가 담당 부서 조치요청서(DOCX)를 만든다 / ⑥ ④통합이 관제 카드와 브리핑을 쓴다 / ⑦ 운영자가 조치 상태를 바꾸면 다음 주기 판정에 반영된다 |
| 핵심기능 3~5개 | 1) QR 민원 접수와 개인정보 마스킹 2) LLM 유형 분류와 기억 참고 3) 결정적 심각도 판정(규칙 S-01~S-06, 경계 규칙 B-01~B-04, 계산식 공개) 4) 관제 '지금 조치할 일' 카드와 통합 브리핑 5) 담당 부서 조치요청서 DOCX 자동 생성 |
