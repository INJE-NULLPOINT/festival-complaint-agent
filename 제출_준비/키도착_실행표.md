# API 키 도착일 실행표

> 키(`ANTHROPIC_API_KEY`)가 오는 날 이 순서대로 한 번에 끝냅니다.
> 대상: D5-1 · D5-2 · D6-1 · D6-3 · D6-5 · 분류 방식 결정(A / B′) · API 인젝션 재확인.
> 작성 2026-09-30 (참모). 명령은 `festival_agent` 폴더, PowerShell 기준입니다.

## 읽는 법

- **시간·비용의 '추정'**은 지금까지의 Claude Code CLI 기록에서 옮긴 값입니다. API로 재 본 적이 없으니 첫 실행 결과로 바로 고칩니다.
  - 참고 기록 1: CLI 정확도 측정 1회(합성 32건) 호출 6회, 입력 14,159 · 출력 3,733 · 캐시 읽기 13,287 토큰, 약 $0.134 (`tests/accuracy_report.md`)
  - 참고 기록 2: CLI 워커 1주기 약 $0.43 (`제출_준비/원가측정_참고.md`)
  - API 호출 1회 시간은 [서버] 추정으로 약 2.5~3초입니다(CLI는 약 7~8초).
- **운영 DB(`festival.db`)는 6단계 전까지 쓰지 않습니다.** 측정은 모두 임시 DB나 시연 DB에서 돕니다.
- 키 값은 `.env`에만 넣습니다. 채팅·문서·커밋에 적지 않습니다.
- **멈춤 규칙:** 어느 단계든 누적 비용이 **$10**(설계값, 사람이 바꿔도 됨)을 넘으면 멈추고 총괄에게 알립니다.

## 1. 키 확인 — D5-1

```powershell
# .env 에 ANTHROPIC_API_KEY=... 한 줄 (사람이 직접)
python cli.py check
```

- 시간 1분 · 비용 거의 0 (키 확인용 최소 호출)
- 주의: 출력에 키 끝 6자리가 보입니다. 화면 녹화·공유 중에는 돌리지 않습니다.
- 통과: 오류 없이 키 유효 · 백엔드 `anthropic`
- 실패하면: 401/403 → 키 오타나 권한 문제라 사람이 다시 발급받습니다. 결제·한도 오류 → 콘솔에서 사용량 한도를 확인합니다. **여기서 막히면 이후 단계는 모두 하지 않습니다.**

## 2. 정확도 — A(기본) 3회 · D6-3

```powershell
$env:LLM_BACKEND="anthropic"; $env:CLASSIFY_MODE="agent"
python scripts/measure_accuracy.py --backend anthropic --repeat 3
Copy-Item tests/accuracy_report.md output/keyday/accuracy_A.md
```

- 시간 추정 5~10분 · 비용 추정 약 $0.4 (1회 약 $0.13 × 3)
- 기록: `tests/accuracy_report.md`의 `## anthropic` 절 + 사본 `output/keyday/accuracy_A.md`
- 통과: 3회 모두 미처리 0건 · 안전 재현율 4/4. 정확도는 값과 Wilson 95% 신뢰구간 그대로 적습니다(합성 32건이라 85% 목표 판정에는 쓰지 않습니다. 실제 평가셋은 D6-6 뒤에 따로 돌립니다).
- 실패하면: 429(속도 제한) → `--batch 10`으로 낮춰 다시. 미처리가 남으면 워커·임시 DB 문제라 [서버]에게 넘깁니다.

## 4. 지연 — A · B′ 벽시계

```powershell
# 서버가 0단계에서 옮긴 scripts/wall_clock.py 로 (사용법은 README)
$env:LLM_BACKEND="anthropic"; $env:CLASSIFY_MODE="agent";    python scripts/wall_clock.py   # A
$env:LLM_BACKEND="anthropic"; $env:CLASSIFY_MODE="prefetch"; python scripts/wall_clock.py   # B′
```

- 시간 추정 10분 · 비용 추정 $0.5 미만
- 측정값: **접수(`feedback.ingested_at`) → 분류 완료(`classification.processed_at`) 벽시계, 워커 폴링 포함**의 중앙값과 최댓값. 1건과 5건 각각 3회. 호출 시간만 재면 안 됩니다(D6-5 [참모 · 지연안]).
- 기록: `output/keyday/latency.md` (A·B′ 표)

## 5. 분류 방식 결정 (A / B′)

| 조건 | 결정 |
|---|---|
| A 벽시계 **중앙값 ≤ 10초이고 최댓값 ≤ 15초** | **A 유지** (기본값 그대로, 구조 변경 없음) |
| A가 넘고 B′가 위 조건을 만족하며, B′ 정확도·안전 재현율이 A보다 낮지 않음 | **B′로 전환** (`config.CLASSIFY_MODE` 한 줄 — [서버]) |
| 둘 다 넘음 | **A 유지 + '10초 목표 미달'로 문서에 그대로 적음**(값 병기) |

- 15초 상한은 설계값입니다([확인 필요: 총괄 결정]).
- 결정 뒤 고른 쪽의 사본을 되돌립니다: `Copy-Item output/keyday/accuracy_<A|Bprime>.md tests/accuracy_report.md`.
- B′로 바꾸면 도구 수가 달라집니다(분류기에서 `get_pending` 빠짐). 문서의 '도구 14종'·발표 2장을 [총괄]이 고칩니다. B′에서도 `lookup_similar`를 부른 기록이 없으면 '애매할 때 과거 사례 조회'는 성과로 쓰지 않습니다.
