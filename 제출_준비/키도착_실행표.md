# API 키 도착일 실행표

> 키(`ANTHROPIC_API_KEY`)가 오는 날 이 순서대로 한 번에 끝냅니다.
> 대상: D5-1 · D5-2 · D6-1 · D6-3 · D6-5 · 분류 방식 재확인(기본 B′) · API 인젝션 재확인.
> 작성 2026-09-30 (참모). 명령은 `festival_agent` 폴더, PowerShell 기준입니다.

## 읽는 법

- **시간·비용의 '추정'**은 지금까지의 Claude Code CLI 기록에서 옮긴 값입니다. API로 재 본 적이 없으니 첫 실행 결과로 바로 고칩니다.
  - 참고 기록 1: CLI 정확도 측정 1회(합성 32건) 모델 호출 4회 · 입력 5,046 · 출력 3,639 · 캐시 읽기 6,183 토큰 · 약 $0.0942 (`tests/accuracy_report.md`)
  - 참고 기록 2: CLI 워커 1주기 약 $0.43 (`제출_준비/원가측정_참고.md`)
  - API 호출 1회 시간은 [서버] 추정으로 약 2.5~3초입니다(CLI는 약 7~8초).
- **운영 데이터는 Supabase에 있습니다(2026-09-30 연결). 9단계 전까지 운영 Supabase에 쓰지 않습니다.** 측정은 모두 임시 SQLite나 시연 DB에서 돕니다. 측정 스크립트(`measure_accuracy`·`test_scenarios`·`wall_clock`·`attack_check`·`demo_scenario`)는 스스로 `SUPABASE_DB_URL`을 비우고 SQLite로 돕니다.
- 키 값은 `.env`에만 넣습니다. 채팅·문서·커밋에 적지 않습니다.
- **멈춤 규칙:** 어느 단계든 누적 비용이 **$10**(설계값, 사람이 바꿔도 됨)을 넘으면 멈추고 총괄에게 알립니다.

## 1. 키 확인 — D5-1

```powershell
# .env 에 ANTHROPIC_API_KEY=... 한 줄 (사람이 직접)
node server/cli.ts check
```

- 시간 1분 · 비용 거의 0 (키 확인용 최소 호출)

- 실패하면: 401/403 → 키 오타나 권한 문제라 사람이 다시 발급받습니다. 결제·한도 오류 → 콘솔에서 사용량 한도를 확인합니다. **여기서 막히면 이후 단계는 모두 하지 않습니다.**

## 2. 정확도 — B′(기본, prefetch) 3회 · D6-3

> 2026-10-01(D5-69)부터 분류 기본은 B′(호출 1회)입니다. `CLASSIFY_MODE` 를 주지 않으면 B′ 로 돕니다.

```powershell
$env:LLM_BACKEND="anthropic"; $env:CLASSIFY_MODE="prefetch"
node server/scripts/measure_accuracy.ts --backend anthropic --repeat 3
Copy-Item tests/accuracy_report.md output/keyday/accuracy_Bprime.md
```

- 시간 추정 5~10분 · 비용 추정 약 $0.4 (1회 약 $0.13 × 3)
- 기록: `tests/accuracy_report.md`의 `## anthropic` 절 + 사본 `output/keyday/accuracy_Bprime.md`
- 통과: 3회 모두 미처리 0건 · 안전 재현율 4/4. 정확도는 값과 Wilson 95% 신뢰구간 그대로 적습니다(합성 32건이라 85% 목표 판정에는 쓰지 않습니다. 실제 리뷰는 수집하지 않으므로 실제 평가셋 측정은 없습니다).
- 실패하면: 429(속도 제한) → `--batch 10`으로 낮춰 다시. 미처리가 남으면 워커·임시 DB 문제라 [서버]에게 넘깁니다.

## 4. 지연 — B′(기본) 벽시계 (+ 필요하면 A)

```powershell
# 서버가 0단계에서 옮긴 server/scripts/wall_clock.ts 로 (사용법은 README)
node server/scripts/wall_clock.ts --backend anthropic --mode prefetch --n 20 --batch 0 --report   # B′(기본) 20회 → tests/wall_clock_report.md (중앙값·p90·최대)
node server/scripts/wall_clock.ts --backend anthropic --mode agent --n 20 --batch 0   # A (5단계에서 필요할 때만)
```

- 시간 추정 15분 · 비용 추정 $1 미만 (추정 — 20회라 늘어남)
- 측정값: **접수(`feedback.ingested_at`) → 분류 완료(`classification.processed_at`) 벽시계, 워커 폴링 포함**의 **중앙값과 p90**(최댓값도 함께). **20회 이상** — 5회로는 CLI·API 호출 편차를 단정할 수 없음(심사위원 제안, 10-01). p90 = 정렬한 N개 중 ceil(0.9×N) 번째 값(보간 없음) — `wall_clock.ts` 가 요약 줄에 적고 `sync_numbers.ts` 가 `llm_latency_p90`·`llm_n` 으로 문서에 반영. 측정 문장은 서로 다른 가상 민원 24개라 20회는 모두 다른 문장입니다. 25회째부터는 같은 문장에 '(N번째 시험)'을 붙여 이어 쓰며(최대 200회), 덧붙은 글이라 기억이 LLM 을 건너뛰지 않으므로 지연 값에 치우침은 없습니다. 예상 시간 claude_code 20회 약 4~5분. 호출 시간만 재면 안 됩니다(D6-5 [참모 · 지연안]).
- 기록: `tests/wall_clock_report.md`(B′, `sync_numbers.ts` 가 문서의 `llm_latency_*` 를 이 파일로 갱신) + 사본 `output/keyday/latency.md`

## 5. 분류 방식 재확인 (기본 B′)

| 조건 | 결정 |
|---|---|
| B′ 벽시계(20회 이상) **중앙값 ≤ 10초이고 p90 ≤ 10초**, 안전 재현율 4/4 | **B′ 유지** (지금 기본 그대로) — 목표 달성 |
| B′ 가 넘음 → 3단계·4단계로 A 를 재서, A 가 위 조건을 만족하고 정확도·안전 재현율이 B′ 보다 낮지 않음 | **A 로 전환** (`CLASSIFY_MODE=agent` 한 줄 — [서버]) — 다시 판단 |
| 둘 다 넘음 | **B′ 유지 + '10초 목표 미달'로 문서에 그대로 적음**(중앙값·p90·최댓값 병기) |

- 총괄 결정(10-01, 09-30 의 '최댓값 ≤ 15초'를 바꿈): 목표 달성 = 중앙값 ≤ 10초이고 p90 ≤ 10초. 신청서 목표 '접수 후 10초 이내'에 대부분(90%)이 드는지를 봅니다. **최댓값은 판정에 쓰지 않고 기록만** 하며, 15초를 넘으면 원인(콜드스타트 등)을 적습니다.
- 결정 뒤 고른 쪽의 사본을 되돌립니다: `Copy-Item output/keyday/accuracy_<A|Bprime>.md tests/accuracy_report.md`.
- A 로 바꾸면 분류의 모델 도구가 1개 → 3개가 됩니다(`get_pending`·`lookup_similar` 추가, 기억 조회가 시스템 도구에서 모델 도구로). 문서의 도구 수·발표 2장을 [참모]가 고칩니다. 과거 사례 조회는 두 모드 모두 코드(기억)가 먼저 합니다.

## 8. 원가 — D6-5

> ⚠ 워커는 **반드시 `--sqlite <임시 파일>`** 로 켭니다. 옵션 없이 켜면 `.env`의 `SUPABASE_DB_URL`을 읽어 **운영 Supabase에 합성 민원을 쓰고 운영 기록으로 원가를 셉니다**(`DB_PATH`만 줘서는 막지 못합니다).
> ⚠ `--sqlite` 뒤의 **경로를 빼먹으면 `festival.db`(기본 파일)를 씁니다.** 합성 민원이 그 파일에 섞이니 아래처럼 `output/keyday/cost.db` 를 꼭 적습니다. 켜진 직후 `DB: SQLite cost.db` 가 찍혔는지 확인하고, 다른 이름이면 바로 Ctrl+C 합니다.
> PowerShell에서 `$env:SUPABASE_DB_URL=""`로 비우는 방법은 쓰지 않습니다(변수가 지워져 `.env` 값이 다시 읽힘).

```powershell
node server/scripts/demo_scenario.ts --db output/keyday/cost.db --reset --no-wait
$env:LLM_BACKEND="anthropic"
node server/worker.ts --sqlite output/keyday/cost.db   # 'DB: SQLite cost.db' 확인 → 약 10분 둔 뒤 Ctrl+C
node server/scripts/measure_cost.ts --db output/keyday/cost.db --note "합성 시나리오 24건 · 약 10분 · 워커 주기 60초 · CLASSIFY_MODE=<결정>"
```

- 시간 약 15분 · 비용 추정 약 $2~4 (CLI 1주기 $0.43 × 약 10주기. ④ 건너뜀으로 줄어들 수 있음)
- 기록: `제출_준비/원가측정.md` (API 실측만 이 이름으로 만들어집니다)
- 통과: 분류·배후(②④)·요청서(③) 원가가 에이전트별로 따로 나옴. 비즈니스모델.md 원가 식의 a·b·d를 API 값으로 교체합니다([총괄]).
- ⚠ 합성 시나리오 기준이라는 조건을 문서에 그대로 둡니다. 운영 Supabase로 재지 않습니다.
