## 1. 문제와 사용자

지역 축제의 불편(주차, 화장실, 가격, 안내, 혼잡, 안전)은 매년 반복되지만, 민원은 축제가 끝난 뒤 결산 단계에서야 집계된다. 축제 중에는 구두 보고와 SNS에 흩어져 운영 담당자가 전체를 볼 수 없다. 더 큰 문제는 순서다. 건수로 줄을 세우면 주차처럼 흔한 불만이 위에 오고, 건수는 적지만 사고로 이어질 수 있는 안전 민원이 묻힌다.

주 사용자는 축제 운영 담당 주무관이다(대상 축제 예시: 진주남강유등축제). 방문객은 구역별 QR 코드로 불편을 한 줄 남기고, 조치는 교통과·환경위생과·안전총괄과·지역경제과·관광진흥과 같은 담당 부서가 받는다. 핵심 주장은 한 문장이다. **건수가 아니라 심각도로 판단한다.** 운영자에게 필요한 것은 "무엇이 많은가"가 아니라 "지금 무엇을 먼저 해야 하는가"다.

## 2. Agent 구조

**2경로.** 신청서 목표는 "접수 후 10초 이내 분류·반영"이다. 에이전트 4개를 직렬로 태우면 호출이 쌓이므로 경로를 나눴다. **Fast Path**(실시간): QR 접수 → 개인정보 마스킹 → ①분류 → 화면 반영. **Agent Path**(배후, 주기 실행): ②심각도·감시 → ③조치 → ④통합 → 브리핑. 에이전트 간 작업은 DB 작업 큐로 넘기고 메시지 브로커는 쓰지 않는다.

**에이전트 4종, 도구 14종** (① 분류는 `CLASSIFY_MODE` 기본값 `agent` 기준)

| 에이전트 | 도구 | 하는 판단 |
|---|---|---|
| ① 분류 | `get_pending` `lookup_similar` `save_classification` | 유형·부정강도·안전 여부, 애매하면 확인 필요로 보냄 |
| ② 심각도·감시 | `get_window_stats` `score_label` `save_snapshot` `raise_alert` | 어떤 창을 볼지, 무엇을 알릴지 |
| ③ 조치 | `get_department` `collect_quotes` `lookup_festival_info` `generate_doc` | 인용할 원문 선별, 조치 제안, DOCX 생성 |
| ④ 통합 | `read_agent_results` `rank_actions` `rank_issues` `write_briefing` | 최우선 1건 결정, 카드 문구, 근거 서술 |

에이전트는 역할 프롬프트 + 도구 집합 + Function Calling 루프로 이뤄지며 루프는 프레임워크 없이 직접 구현했다. **판단은 에이전트, 계산은 함수**다: 심각도 점수·등급·순위는 LLM이 계산하지 않고 결정적 함수가 계산하며(같은 입력 → 같은 점수, 계산식 문자열 동반), 에이전트는 도구로 호출만 한다. 건수 1위와 심각도 1위가 다르면 ④가 그 이유를 브리핑에 쓴다.

**분류 호출 최적화(A안).** 분류는 원래 모델 호출이 3번이었다(대기 조회 → 저장 → "저장했습니다" 보고문). 대기 민원이 모두 저장되면 코드가 종료를 판단(`done_when`)해 보고 호출을 없앴다. 도구 로그와 분류 결과는 그대로다. 대기 민원을 코드가 프롬프트에 넣어 호출을 1번으로 줄이는 B′ 모드(`CLASSIFY_MODE=prefetch`)도 구현했지만 기본값은 바꾸지 않았다. 두 모드의 정확도는 같았고(아래), 모델이 `lookup_similar` 를 부른 횟수는 측정에서 **0회**였다 — 이 도구는 "제공되며 호출은 모델 판단"일 뿐 성과로 주장하지 않는다.

**Memory와 Feedback.** `severity` 시계열 스냅숏(추이·급증 판단), 분류 캐시(같은 문장 재호출 방지), `action_request.status` → 조치 없이 30분이 지나면 다음 계산에 ×1.2(S-06), `agent_log`(도구 호출·판단 근거·지연·토큰), 운영자가 처리한 확인 필요 건(`decided_by='operator'`)은 정확도 계산에서 제외.

## 3. 구현

**구성.** TypeScript(Node 24) 서버 코어(에이전트·심각도·카드·DB, `server/`) + TypeScript 웹 앱(Vite, 접수·관제·조치) + 터미널 `cli.ts`. 서버와 웹이 같은 언어라 Python 은 쓰지 않는다. 운영 저장소는 Supabase(Postgres·Realtime·Storage)다. 2026-09-30 에 연결해 스키마·RLS·RPC·Storage `docs` 버킷을 적용했고, 워커와 웹이 모두 Supabase 에 붙는다. 같은 코드가 `SUPABASE_DB_URL` 이 없으면 SQLite(WAL)로 돌며, `webapi.ts` 는 Supabase 의 읽기·RPC·실시간·파일 저장을 흉내 내는 **개발·테스트용 local 대역**이다(화면 점검·시나리오·정확도 측정은 운영 데이터를 건드리지 않도록 이쪽 임시 DB 로 돈다). 모델은 `claude-opus-5-5`, 코드 줄 수는 서버 TypeScript 8,729줄(테스트 제외) · 웹 TypeScript 2,359줄 · CSS 1,020줄 · SQL 648줄이고, 테스트는 서버 TypeScript 2,678줄 · 화면 점검 스크립트 1,927줄이다(빈 줄·주석 포함, 2026-10-01 작업 트리 기준 — Streamlit 화면 제거·서버 TS 전환 뒤).

**개발계획서와 달라진 점 — 화면.** 개발계획서(신청서)에는 관리자 화면을 Streamlit 으로 적었으나, 개발 중 **웹(Vite + TypeScript) + Supabase(Postgres·Realtime·Storage) 구성으로 바꾸고 Streamlit 화면은 뺐다**(2026-10-01). 이유는 네 가지다. ①실시간 반영 — 관제가 새로고침 없이 바뀐 부분만 다시 그린다(Supabase Realtime, 키가 없을 때는 `webapi.ts` 의 SSE 로 같은 동작). ②모바일 접수 — 방문객이 QR 로 여는 접수 화면을 휴대폰 폭에 맞춰 만들고 구형 브라우저용 빌드를 따로 낸다. ③운영자 코드 보호 — 관리자 동작을 서버 쪽 RPC 에서 코드로 막아 방문객 화면과 분리한다. ④배포 — 정적 웹 빌드 + Supabase 라 별도 앱 서버 없이 올릴 수 있다. Supabase 는 2026-09-30 에 연결해 지금 운영 구성으로 쓴다. 아직 남은 변경은 하나다: LLM 을 마지막에 Claude API 로 바꾼다(지금 측정은 Claude Code CLI 경유).

**개발계획서와 달라진 점 — 서버 언어.** 개발계획서에는 서버(에이전트·심각도·DB)를 Python 으로 적었으나, **TypeScript(Node 24)로 통일했다**(2026-10-01). 이유는 세 가지다. ①한 언어 — 웹과 서버가 같은 언어라 한 사람이 양쪽을 읽고 고칠 수 있다. ②타입 공유 — 카드·민원·RPC 인자 같은 자료 모양을 웹과 서버가 같은 정의로 맞춘다. ③배포 단순화 — Node 하나만 설치하면 되고(빌드 단계 없이 `.ts` 를 바로 실행), Python 가상환경·패키지를 따로 챙기지 않는다. 옮길 때는 모듈 구조·함수 이름·동작을 1:1 로 유지하고, 단위 테스트와 대표 Test Case 5종을 같은 입력·같은 기대값으로 TS 로 옮겼다. **Python 판과 TS 판을 개발용 시드 160건으로 한 바퀴 돌려 결과를 비교했고 차이는 0건이었다.** 확인 뒤 Python 코드는 저장소에서 지웠다.

| S-02 | 안전 관련 ×2.0 |

**규칙의 근거.** 가중치·문턱값(60/40, ×2.0, ×1.5, ×1.2, 3건, B-01~B-04)은 데이터로 맞춘 값이 아니라 운영 우선순위를 옮긴 **설계값**이다. 각 값을 ±20% 바꿔도 결론(건수 1위 주차보다 심각도 1위 안전)이 유지됨을 확인했다(합성 시드 기준). 규칙의 **방향**은 다음 공문서와 맞춘다. 근거 목록은 `제출_준비/심각도_기준_양식.md` 9절에 있다.

- **혼잡을 안전으로 보는 이유(S-02).** 「재난 및 안전관리 기본법」 제3조 제1호 나목은 다중운집인파사고를 사회재난에 넣었다(행안부 「다중운집인파사고 안전관리 가이드라인」 2024.9, p.1). 그래서 혼잡(crowd)을 안전 계열로 묶어 ×2.0 을 준다. 유등축제는 순간 최대 관람객 1천 명 이상·수면 개최·불꽃놀이로 「재난안전법 시행령」 제73조의9 의 안전관리계획 대상에도 해당한다.
- **인파 단계와 급증(S-03·S-04).** 가이드라인은 인파 위험을 여유·주의·위험 3단계로 나누고, '주의'(흐름 정체)에서 안내방송·요원 투입·일방통행을 한다(p.11). 민원으로는 밀집도를 잴 수 없어 숫자를 옮기지는 않았다. 대신 안전 3건이면 곧바로 즉시 등급으로 올리는 S-04 로 '위험 단계 전에 조치한다'는 취지를 따른다. 행안부 인파관리지원시스템은 평소 대비 비율로 단계를 나눈다(「지역축제장 안전관리 매뉴얼(2024)」 p.82, 200% 이상 '혼잡'). 우리 급증 규칙 '직전 평균의 2배'도 같은 방식으로 본다. 2배와 200% 문턱을 맞춘 것은 우리 해석이다.
- **미조치 30분(S-06).** 「민원 처리에 관한 법률 시행령」 제19조는 '즉시' 처리 민원을 3근무시간 이내로 정한다. 축제 현장 안전은 이보다 빨라야 하므로 30분을 설계값으로 둔다(법이 30분을 정한 것은 아니다).
- **고위험 조치는 사람이 판단.** 진입통제·대피 유도·도로 통제는 가이드라인 '위험' 단계 조치다. 재난문자는 「재난문자방송 기준 및 운영규정」(행안부 예규 제361호) 제9조에 따라 현장상황 판단에 따라 정해진 기관이 보낸다. 그래서 AI 는 이런 조치를 안전·즉시 카드에서만 '제안'하고 '운영자 판단 필요'를 붙인다. 교통통제·대피 유도는 경찰·소방 몫이라 요청서에는 협조 요청으로만 적는다(재난안전법 제66조의11 제5항).
- 이 근거는 규칙이 향하는 방향을 뒷받침할 뿐, 숫자 자체를 법이 정한 것은 아니다. 실제 운영 데이터가 쌓이면 다시 맞춘다. 인파관리지원시스템도 지자체가 현장에 맞게 임계치를 정한다(행안부 2023.12.27).

**관제 '지금 조치할 일' 카드 (D5-29).** 유형×구역 단위 카드로 "문제·위치·우선순위·해야 할 일"을 보여준다. 등급은 유형 등급을 물려받고 정렬은 (조치 그룹, 등급, 안전 계열 먼저, 점수, 시각)이다. 카드의 AI 문장은 상위 3장에만 붙고, 코드가 검사한다: 인용한 민원이 실제 근거 후보인지, 조치 2~4개, 숫자·지어낸 시설·원문 복사 금지, 중단·대피 같은 고위험 표현은 안전·즉시 등급에서만 허용하되 '운영자 판단 필요' 표시. 검사에 실패하면 템플릿 문구로 대신한다. 건수·마지막 시각·최신 민원은 LLM 없이 5초 주기로 갱신한다.

**민원 지우기와 확인 필요 처리 (D5-30·32).** 운영자는 장난·개인정보 노출 민원을 지울 수 있고(숨김, 되돌리기 가능, 모든 집계에서 제외), 신뢰도 0.3 미만이거나 내용이 없어 유형을 못 정한 건은 '확인 필요'로 분리된다. 확인 필요는 세 가지로 처리한다: 유형 지정 · 유형 없음으로 닫기 · 지우기(되돌리기 가능). 안전 의심 확인 필요가 15분 넘게 방치되면 알림이 한 번 뜬다.

**운영자 코드 (D5-31).** 지우기·확인 필요 처리·조치 상태 변경·요청서 생성은 운영자 코드가 있어야 한다(`.env`의 `ADMIN_CODE`, 비면 전부 거부, 5회 실패 시 10분 잠금). 방문객 접수는 코드 없이 된다. 웹 local 대역(`webapi.ts`)과 Supabase RPC가 같은 규칙을 쓴다.

**개인정보·안전.** QR 접수는 이름·연락처를 받지 않는다. 저장 전에 연락처·주민번호·카드번호·이메일·차량번호를 가리고, 웹 접수 원문은 접수함에 잠깐 머물다 마스킹 후 옮긴 직후 지운다. 민원 본문은 데이터로만 다룬다. 프롬프트 인젝션은 "지시 대상(AI·시스템)과 명령이 함께 있을 때"만 탐지해 카드 근거에서 제외하고(평범한 민원을 지시문으로 오인하지 않게 좁힘), 조치 문구 검사와 결정적 등급 계산이 뒤에서 받친다.

**조치요청서.** 담당 부서, 건수 요약, 원문 인용 5건, 조치 제안, 판정 계산식을 담은 DOCX를 만든다. 같은 유형의 새 요청서는 이전 열린 요청을 `superseded` 로 닫는다.

**백엔드 전환.** `.env`의 `LLM_BACKEND` 한 줄로 전환한다: `anthropic`(실제 모델, 제출본) / `claude_code`(`claude -p` 경유, 개발용 — 로그는 `cli_call` 로 분리) / `local`(규칙 기반 대역, 개발·리허설용, 제출물 아님 — 코드·로그·README·화면에 표시). 관제 화면 머리에 데이터 연결·분류 백엔드·합성 데이터 재생 여부가 배지로 뜬다.

**외부 API·리플레이.** 한국관광공사 TourAPI 4.0을 도구로 연동했고 실패 시 캐시→수기 구역 시드로 대체한다 [확인 필요: 키 발급]. 리플레이 엔진은 시각이 기록된 민원을 배속으로 재생해 며칠치 유입 속 순위 변화를 검증한다.

## 5. 성과

**E2E 관통.** 접수 → 분류 → 심각도 → 알림 → 조치 카드·요청서(DOCX) → 브리핑까지 전 구간이 한 줄로 이어진다.

**심각도 역전 재현 (합성 시드·규칙 기반 대역 분류 — AI 모델 아님).** 개발용 합성 시드 전체를 4일(5760분) 창으로 재생하면 건수 1위와 심각도 1위가 갈린다. 주차/교통은 53건으로 건수 1위지만 56.9점(3위), 안전은 11건뿐인데 93.2점으로 1위, 2위는 혼잡 3건(70.4점)이다. 분류 신뢰도가 낮은 5건은 확인 필요로 빠져 집계에 없다. 안전 점수의 계산식: `(0.08×60 + 0.85×40) × 안전2.0 × 급증1.0 × 미조치1.2 = 93.2`. 시연 영상은 이 수치가 아니라 합성 시나리오(`server/scripts/demo_scenario.ts`, 배경 가상 민원 24건 + 실시간 입력)로 역전 장면을 재현하며 합성임을 자막으로 밝힌다. [확인 필요: 실제 모델·실제 시드로 재현]

**실제 모델 동작 확인(CLI 경유).** 에이전트 4종을 한 바퀴 돌렸다. ①은 인젝션 문장을 무시하고 신뢰도를 낮췄고, ②는 도구를 7회 호출해 알림 3건을 냈고, ③은 인용 5건·제안 3건의 요청서를, ④는 브리핑과 카드 문구를 만들었다. 실제 모델이 카드 문구에서 공격 문장을 따르지 않고 인용도 하지 않는 것을 공격 문장 3종으로 확인했다. API 키 경로는 [확인 필요].

**처리 원가.** 민원 1건 처리 원가는 [확인 필요: API 실측]. CLI 경유 참고값(`원가측정_참고.md`, 1주기 $0.43)은 호출마다 자체 프롬프트가 붙어 API와 금액이 다르므로 성과로 쓰지 않는다.

**실사용자 검증.** [확인 필요: 3명 이상 피드백, 이름·소속, 검증일자]

- **지연 목표 미달**: CLI 경유로는 접수→분류가 10초 안팎을 넘는다. API 전환 시 단축이 예상되나 미측정이다.
- **`lookup_similar`**: 제공되는 도구이지만 실측에서 모델이 부르지 않았다. 애매한 문장의 처리는 신뢰도 낮춤→확인 필요 경로가 맡는다.
- **부서 연락처는 가짜 번호**: `DEPARTMENT_MAP` 의 부서명은 「지역축제장 안전관리 매뉴얼(2024)」의 상황실 편성 예시(p.137·154~155)를 참고한 예시이고, 번호 055-000-000x 는 **실제 번호가 아니다**. 요청서 DOCX 에 그대로 찍힌다. 실제 운영 때는 시청 공개 대표번호로 바꿔야 한다.
- **가중치는 설계값**: 위 '규칙의 근거'대로 법·매뉴얼은 방향의 근거이고 숫자는 설계값이다.
- **Supabase**: 2026-09-30 에 연결했다. 자동 화면 점검(`run_all.ts`)은 local 대역에서 돌므로, Supabase 경로(`data-supabase.ts`·RLS·RPC)의 화면 흐름은 사람 확인과 운영 로그로 확인한다. 출처별 폭주 제한은 `x-forwarded-for` 헤더에 의존해 실제 접속자 주소가 오는지 [확인 필요].
- **현장 검증 부재**: 실제 축제 기간에 운영한 적은 없다. 범위는 대회 Level 3 MVP이며 상용 수준의 보안·대규모 운영은 범위 밖이다.
