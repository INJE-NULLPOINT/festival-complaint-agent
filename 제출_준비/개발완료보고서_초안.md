## 1. 문제와 사용자

지역 축제의 불편(주차, 화장실, 가격, 안내, 혼잡, 안전)은 매년 반복되지만, 민원은 축제가 끝난 뒤 결산 단계에서야 집계된다. 축제 중에는 구두 보고와 SNS에 흩어져 운영 담당자가 전체를 볼 수 없다. 더 큰 문제는 순서다. 건수로 줄을 세우면 주차처럼 흔한 불만이 위에 오고, 건수는 적지만 사고로 이어질 수 있는 안전 민원이 묻힌다.

주 사용자는 축제 운영 담당 주무관이다(대상 축제 예시: 진주남강유등축제). 방문객은 구역별 QR 코드로 불편을 한 줄 남기고, 조치는 교통과·환경위생과·안전총괄과·지역경제과·관광진흥과 같은 담당 부서가 받는다. 핵심 주장은 한 문장이다. **건수가 아니라 심각도로 판단한다.** 운영자에게 필요한 것은 "무엇이 많은가"가 아니라 "지금 무엇을 먼저 해야 하는가"다.

## 2. Agent 구조

**2경로.** 신청서 목표는 "접수 후 10초 이내 분류·반영"이다. 에이전트 4개를 직렬로 태우면 호출이 쌓이므로 경로를 나눴다. **Fast Path**(실시간): QR 접수 → 개인정보 마스킹 → ①분류 → 화면 반영. **Agent Path**(배후, 주기 실행): ②심각도·감시 → ③조치 → ④통합 → 브리핑. 에이전트 간 작업은 DB 작업 큐로 넘기고 메시지 브로커는 쓰지 않는다.

**에이전트 4종, 도구 14종** (① 분류는 `CLASSIFY_MODE` 기본값 `agent` 기준)

| 에이전트 | 도구 | 하는 판단 |
|---|---|---|
| ① 분류 | `get_pending` `lookup_similar` `save_classification` | 유형·부정강도·안전 여부, 애매하면 확인 필요로 보냄 |
| ② 심각도·감시 | `get_window_stats` `score_label` `save_snapshot` `raise_alert` | 어떤 창을 볼지, 무엇을 알릴지 |
| ③ 조치 | `get_department` `collect_quotes` `lookup_festival_info` `generate_doc` | 인용할 원문 선별, 조치 제안, DOCX 생성 |
| ④ 통합 | `read_agent_results` `rank_actions` `rank_issues` `write_briefing` | 최우선 1건 결정, 카드 문구, 근거 서술 |

에이전트는 역할 프롬프트 + 도구 집합 + Function Calling 루프로 이뤄지며 루프는 프레임워크 없이 직접 구현했다. **판단은 에이전트, 계산은 함수**다: 심각도 점수·등급·순위는 LLM이 계산하지 않고 결정적 함수가 계산하며(같은 입력 → 같은 점수, 계산식 문자열 동반), 에이전트는 도구로 호출만 한다. 건수 1위와 심각도 1위가 다르면 ④가 그 이유를 브리핑에 쓴다.

**분류 호출 최적화(A안).** 분류는 원래 모델 호출이 3번이었다(대기 조회 → 저장 → "저장했습니다" 보고문). 대기 민원이 모두 저장되면 코드가 종료를 판단(`done_when`)해 보고 호출을 없앴다. 도구 로그와 분류 결과는 그대로다. 대기 민원을 코드가 프롬프트에 넣어 호출을 1번으로 줄이는 B′ 모드(`CLASSIFY_MODE=prefetch`)도 구현했지만 기본값은 바꾸지 않았다. 두 모드의 정확도는 같았고(아래), 모델이 `lookup_similar` 를 부른 횟수는 측정에서 **0회**였다 — 이 도구는 "제공되며 호출은 모델 판단"일 뿐 성과로 주장하지 않는다.

**Memory와 Feedback.** `severity` 시계열 스냅숏(추이·급증 판단), 분류 캐시(같은 문장 재호출 방지), `action_request.status` → 조치 없이 30분이 지나면 다음 계산에 ×1.2(S-06), `agent_log`(도구 호출·판단 근거·지연·토큰), 운영자가 처리한 확인 필요 건(`decided_by='operator'`)은 정확도 계산에서 제외.

## 3. 구현

**구성.** Python 코어(에이전트·심각도·카드·DB) + Streamlit 화면 3종 + 터미널 `cli.py` + TypeScript 웹 앱(접수·관제·조치). 저장소는 SQLite(WAL, 16테이블)이고 Supabase Postgres로 코드 수정 없이 전환할 수 있다(스키마는 Postgres 파서로 정적 검증, 실제 Supabase 적용은 [확인 필요: 키]). 웹 앱은 키 없이도 `webapi.py` 가 Supabase의 읽기·RPC·실시간·파일 저장을 흉내 내 돈다. 모델은 `claude-opus-5-5`, 코드 줄 수는 Python 8,401줄(테스트 제외) · 웹 TypeScript 1,948줄 · CSS 845줄 · SQL 567줄이고, 테스트는 Python 2,414줄 · 화면 점검 스크립트 1,325줄이다(git 추적 파일, 빈 줄·주석 포함, 2026-09-30 커밋 464e150 기준).

**심각도 규칙과 경계 규칙.**

| ID | 규칙 |
|---|---|
| S-01 | 기본점수 = 창 안의 빈도 60% + 부정강도 40% |
| S-02 | 안전 관련 ×2.0 |
| S-03 | 급증 ×1.5 (최근 15분 유입률 ≥ 직전 60분 평균 × 2) |
| S-04 | 안전 3건 이상이면 점수와 무관하게 `immediate` |
| S-05 | 긍정은 심각도 계산에서 제외 |
| S-06 | 미조치 30분 경과 ×1.2 |
| B-01~B-04 | 창 안 10건 미만이면 빈도비 하한(1건=100% 방지) · 급증은 최근 3건 이상 · 비안전 즉시 등급은 5건 이상이고 상한 79.9 · 안전 1건은 최소 high(60) |

**관제 '지금 조치할 일' 카드 (D5-29).** 유형×구역 단위 카드로 "문제·위치·우선순위·해야 할 일"을 보여준다. 등급은 유형 등급을 물려받고 정렬은 (조치 그룹, 등급, 안전 계열 먼저, 점수, 시각)이다. 카드의 AI 문장은 상위 3장에만 붙고, 코드가 검사한다: 인용한 민원이 실제 근거 후보인지, 조치 2~4개, 숫자·지어낸 시설·원문 복사 금지, 중단·대피 같은 고위험 표현은 안전·즉시 등급에서만 허용하되 '운영자 판단 필요' 표시. 검사에 실패하면 템플릿 문구로 대신한다. 건수·마지막 시각·최신 민원은 LLM 없이 5초 주기로 갱신한다.

**민원 지우기와 확인 필요 처리 (D5-30·32).** 운영자는 장난·개인정보 노출 민원을 지울 수 있고(숨김, 되돌리기 가능, 모든 집계에서 제외), 신뢰도 0.3 미만이거나 내용이 없어 유형을 못 정한 건은 '확인 필요'로 분리된다. 확인 필요는 세 가지로 처리한다: 유형 지정 · 유형 없음으로 닫기 · 지우기(되돌리기 가능). 안전 의심 확인 필요가 15분 넘게 방치되면 알림이 한 번 뜬다.

**운영자 코드 (D5-31).** 지우기·확인 필요 처리·조치 상태 변경·요청서 생성은 운영자 코드가 있어야 한다(`.env`의 `ADMIN_CODE`, 비면 전부 거부, 5회 실패 시 10분 잠금). 방문객 접수는 코드 없이 된다. 웹 local 대역·Streamlit·Supabase RPC가 같은 규칙을 쓴다.

**개인정보·안전.** QR 접수는 이름·연락처를 받지 않는다. 저장 전에 연락처·주민번호·카드번호·이메일·차량번호를 가리고, 웹 접수 원문은 접수함에 잠깐 머물다 마스킹 후 옮긴 직후 지운다. 민원 본문은 데이터로만 다룬다. 프롬프트 인젝션은 "지시 대상(AI·시스템)과 명령이 함께 있을 때"만 탐지해 카드 근거에서 제외하고(평범한 민원을 지시문으로 오인하지 않게 좁힘), 조치 문구 검사와 결정적 등급 계산이 뒤에서 받친다.

**조치요청서.** 담당 부서, 건수 요약, 원문 인용 5건, 조치 제안, 판정 계산식을 담은 DOCX를 만든다. 같은 유형의 새 요청서는 이전 열린 요청을 `superseded` 로 닫는다.

**백엔드 전환.** `.env`의 `LLM_BACKEND` 한 줄로 전환한다: `anthropic`(실제 모델, 제출본) / `claude_code`(`claude -p` 경유, 개발용 — 로그는 `cli_call` 로 분리) / `local`(규칙 기반 대역, 개발·리허설용, 제출물 아님 — 코드·로그·README·화면에 표시). 관제 화면 머리에 데이터 연결·분류 백엔드·합성 데이터 재생 여부가 배지로 뜬다.

**외부 API·리플레이.** 한국관광공사 TourAPI 4.0을 도구로 연동했고 실패 시 캐시→수기 구역 시드로 대체한다 [확인 필요: 키 발급]. 리플레이 엔진은 시각이 기록된 민원을 배속으로 재생해 며칠치 유입 속 순위 변화를 검증한다.

표본이 작아 신뢰구간이 넓으므로 참고값일 뿐이다. 실제 평가는 사람 2명이 독립 라벨링한 실제 리뷰 100건 이상(안전 정답 20건 이상)으로 반복 3회, 신뢰구간과 라벨러 간 일치도(κ)를 함께 낼 계획이며 도구는 준비돼 있다(`scripts/measure_accuracy.py --labels`, 라벨링 가이드). 목표는 85% 이상이며 달성 여부는 실측 뒤 판단한다.

**지연(CLI 경유, 임시 DB).** 분류 1건의 모델 호출은 A안 적용으로 23.5초 → 14.8초(호출 3→2회)가 됐다. 접수부터 분류 완료까지 워커 폴링을 포함한 벽시계는 A안(기본) 중앙 17.1초, B′ 중앙 11.2초로 **둘 다 '10초 이내' 목표에 못 미친다**(호출 1번의 바닥이 CLI 기동 때문에 약 6.6초). API 직접 호출 기준은 [확인 필요: API]. 배후 에이전트가 도는 중에도 새 민원이 0.5초 만에 관제 유입에 뜬다(접수·분류·요청서·에이전트를 스레드로 분리). 요청서 생성은 약 50초(CLI 경유).

**개발 중 잡은 버그와 사고.** 전화번호 마스킹 누락(정규식 `\b`가 한글 앞에서 경계가 안 됨), 건수는 누적·심각도는 60분 창으로 서로 다른 모집단 비교, 조치요청서 저장 실패(라벨 `/`가 경로로 해석), 대역에서 TC4가 거짓 통과, 배후 에이전트 때문에 웹 요청·새 민원이 분 단위로 지연, 같은 유형 요청서가 여럿일 때 가장 오래된 상태를 읽은 오판(실제 모델이 브리핑에서 먼저 짚음), 웹 API 포트 중복 실행, 지시문 탐지가 "다들 무시하고 새치기" 같은 정상 민원을 잡던 오탐(지시 대상+명령 조합으로 좁히고 정상 문장 묶음을 테스트로 고정), 카드 문구 검사가 실제 모델의 정당한 표현("어둡다"→"임시 조명")을 막던 문제(동의어 인정).
**복원 사고**: PC 재시작으로 소스 파일 2개가 통째로 NUL 바이트로 바뀌어 웹 API·워커가 뜨지 않았다. 컴파일 캐시(pyc)의 상수와 작업 기록의 수정 이력으로 복원해 바이트코드·테스트로 검증했고, 이후 **git 저장소(비공개 원격)를 도입**해 같은 사고에 대비했다.

## 5. 성과

**E2E 관통.** 접수 → 분류 → 심각도 → 알림 → 조치 카드·요청서(DOCX) → 브리핑까지 전 구간이 한 줄로 이어진다.

**심각도 역전 재현 (합성 시드·규칙 기반 대역 분류 — AI 모델 아님).** 개발용 합성 시드 전체를 4일(5760분) 창으로 재생하면 건수 1위와 심각도 1위가 갈린다. 주차/교통은 53건으로 건수 1위지만 56.9점(3위), 안전은 11건뿐인데 93.2점으로 1위, 2위는 혼잡 3건(70.4점)이다. 분류 신뢰도가 낮은 5건은 확인 필요로 빠져 집계에 없다. 안전 점수의 계산식: `(0.08×60 + 0.85×40) × 안전2.0 × 급증1.0 × 미조치1.2 = 93.2`. 시연 영상은 이 수치가 아니라 합성 시나리오(`scripts/demo_scenario.py`, 배경 가상 민원 24건 + 실시간 입력)로 역전 장면을 재현하며 합성임을 자막으로 밝힌다. [확인 필요: 실제 모델·실제 시드로 재현]

**실제 모델 동작 확인(CLI 경유).** 에이전트 4종을 한 바퀴 돌렸다. ①은 인젝션 문장을 무시하고 신뢰도를 낮췄고, ②는 도구를 7회 호출해 알림 3건을 냈고, ③은 인용 5건·제안 3건의 요청서를, ④는 브리핑과 카드 문구를 만들었다. 실제 모델이 카드 문구에서 공격 문장을 따르지 않고 인용도 하지 않는 것을 공격 문장 3종으로 확인했다. API 키 경로는 [확인 필요].

**처리 원가.** 민원 1건 처리 원가는 [확인 필요: API 실측]. CLI 경유 참고값(`원가측정_참고.md`, 1주기 $0.43)은 호출마다 자체 프롬프트가 붙어 API와 금액이 다르므로 성과로 쓰지 않는다.

**실사용자 검증.** [확인 필요: 3명 이상 피드백, 이름·소속, 검증일자]

## 6. 한계

- **데이터**: 리플레이 시드(`seed/dev_sample.csv`, 160건)와 시연 배경 민원은 개발용 합성이다. 역전 수치도 합성 기준이다. [확인 필요: 실제 수집 시드 교체 여부와 건수·출처]
- **정확도 근거 부족**: 실제 모델·실제 리뷰 기준 정확도가 아직 없다. CLI 참고값은 합성 32건이라 신뢰구간이 넓고 안전 정답은 4건뿐이다.
- **지연 목표 미달**: CLI 경유로는 접수→분류가 10초 안팎을 넘는다. API 전환 시 단축이 예상되나 미측정이다.
- **`lookup_similar`**: 제공되는 도구이지만 실측에서 모델이 부르지 않았다. 애매한 문장의 처리는 신뢰도 낮춤→확인 필요 경로가 맡는다.
- **Supabase**: 스키마는 정적 검증만 했고 실제 적용·RPC 동작은 키 발급 뒤 확인한다.
- **현장 검증 부재**: 실제 축제 기간에 운영한 적은 없다. 범위는 대회 Level 3 MVP이며 상용 수준의 보안·대규모 운영은 범위 밖이다.

## 7. 신규개발분

기존 자산을 붙인 것이 아니라 팀이 새로 만든 부분이다.

- 에이전트 루프·작업 큐 직접 구현(프레임워크 미사용), 2경로 구조, `done_when` 종료 조건
- 심각도 규칙 6종 + 경계 규칙 4종과 계산식 노출, 통합 에이전트의 우선순위 조정·브리핑
- 관제 조치 카드(유형×구역)와 AI 문구 검사, 민원 지우기, 확인 필요 처리, 운영자 코드
- 개인정보 마스킹, 프롬프트 인젝션 탐지, 부서 매핑, 조치요청서 DOCX 생성
- 리플레이 엔진, 시연용 합성 시나리오, 정확도 평가 도구(신뢰구간·κ·평가셋)
- 백엔드 전환 구조(실제 모델 / CLI 경유 / 개발용 대역), Supabase 전환 구조와 local 대역 API 서버, 웹 앱

사용한 외부 요소는 Claude API, 한국관광공사 TourAPI, Streamlit, python-docx, Supabase 등이다. 출처와 AI 활용 내역은 별지2 출처·AI 활용 신고서에 적는다.
