## 1. 문제와 사용자

지역 축제에서는 매년 같은 불편이 반복된다. 주차, 화장실, 가격, 안내, 혼잡, 안전이다. 그런데 이 민원은 축제가 끝난 뒤 결산 단계에서야 집계된다. 축제 중에는 현장 직원의 구두 보고와 SNS에 흩어져 있어, 운영 담당자가 전체를 볼 수 없다. 그래서 대응은 늘 다음 해로 밀린다.

더 큰 문제는 순서다. 민원을 모아도 보통 건수로 줄을 세운다. 그러면 주차처럼 흔한 불만이 맨 위에 오고, 건수는 적지만 사고로 이어질 수 있는 안전 민원은 아래에 묻힌다.

주 사용자는 축제 운영 담당 주무관이다. 대상 축제는 진주남강유등축제를 예시로 삼았다. 방문객은 구역마다 붙은 QR 코드로 불편을 한 줄 남기는 입력자다. 조치를 받는 쪽은 교통과, 환경위생과, 안전총괄과, 지역경제과, 관광진흥과 같은 담당 부서다.

이 과제의 핵심 주장은 한 문장이다. **건수가 아니라 심각도로 판단한다.** 운영자에게 필요한 것은 "무엇이 많은가"가 아니라 "지금 무엇을 먼저 해야 하는가"다.

## 2. Agent 구조

### 2경로 설계

신청서에 "접수 후 10초 이내 분류·반영"을 목표로 적었다. 접수 경로에 에이전트 네 개를 직렬로 태우면 LLM 호출이 쌓여 10초를 넘긴다. 그래서 경로를 둘로 나눴다.

- **Fast Path(실시간)**: QR 접수 → 개인정보 마스킹 → ①분류 에이전트 → 대시보드 반영
- **Agent Path(배후, 주기 실행)**: ②심각도·감시 → ③조치 → ④통합 → 브리핑

에이전트 사이의 작업은 DB 작업 큐(`agent_task`)로 넘긴다. 메시지 브로커는 쓰지 않는다.

### 에이전트 4종과 도구 14개

| 에이전트 | 도구 | 하는 판단 |
|---|---|---|
| ① 분류 | `get_pending` `lookup_similar` `save_classification` | 유형·부정강도·안전 여부 |
| ② 심각도·감시 | `get_window_stats` `score_label` `save_snapshot` `raise_alert` | 어떤 창을 볼지, 무엇을 알릴지 |
| ③ 조치 | `get_department` `collect_quotes` `lookup_festival_info` `generate_doc` | 인용할 원문 선별, 조치 제안, DOCX 생성 |
| ④ 통합 | `read_agent_results` `rank_actions` `write_briefing` | 최우선 1건 결정과 근거 서술 |

각 에이전트는 역할 프롬프트, 도구 집합, Function Calling 루프로 이뤄진다. 루프는 프레임워크 없이 직접 구현했다. 에이전트는 필요한 도구를 스스로 골라 부르고, 필요 없으면 부르지 않는다.

④통합 에이전트가 이 구조의 결론을 낸다. ②는 점수를, ③은 문서를 만들 뿐이다. 운영자에게 필요한 "지금 이것부터 하라"는 한 문장은 ④가 만든다. 건수 1위와 심각도 1위가 다르면, 왜 심각도를 따라야 하는지를 브리핑에 반드시 쓴다.

### 판단은 에이전트, 계산은 함수

심각도 점수, 등급, 우선순위는 LLM이 계산하지 않는다. 결정적 함수(`compute_severity`, `rank_actions`)가 계산하고, 에이전트는 이를 도구로 호출만 한다. 같은 입력에는 항상 같은 점수가 나온다. 함수는 계산식 문자열도 함께 돌려주므로, 화면과 문서에 근거가 그대로 드러난다.

### Memory와 Feedback

- `severity` 시계열 스냅숏: 추이와 급증 판단의 근거
- `lookup_similar`와 분류 캐시: 과거 판단 참조, 같은 문장 재호출 방지
- `action_request.status`: 조치 없이 30분이 지나면 다음 심각도 계산에 ×1.2 가중(S-06)
- `agent_log`: 도구 호출, 판단 근거, 지연, 토큰을 기록

## 3. 구현

### 구성

Python 약 4,034줄이다(`진행현황.md` 기준, 이후 추가분 [확인 필요]). 저장소는 SQLite(WAL, 14테이블)이고, Supabase Postgres로 코드 수정 없이 전환할 수 있다. 화면은 Streamlit 3종(접수·관제·조치), 터미널 인터페이스(`cli.py`), TypeScript 단일 페이지 웹 앱(접수·관제·조치)으로 구성했다. 모델은 `claude-opus-5-5`다.

웹 앱은 Supabase 키가 없어도 돈다. `webapi.py`가 SQLite 위에서 Supabase의 읽기, RPC 3개, 실시간 구독, 파일 저장을 흉내 낸다. RPC 검증 규칙(2~500자, 구역 존재, 부서 매핑, 서울 시각)은 `schema.sql`과 같게 맞췄다. 키가 생기면 `.env` 두 곳만 채워 전환한다.

관제 화면은 현장 요원이 3초 안에 "지금 제일 위험한 것 1개"를 읽도록 위계를 잡았다. 브리핑, 심각도 1위, 알림, 나머지 순이다. 건수 1위와 심각도 1위가 다르면 역전 문구를 띄운다. 글자는 13px 이상, 색 대비는 WCAG AA(라이트·다크 17쌍)를 맞췄다.

### 심각도 규칙 6종

| ID | 규칙 |
|---|---|
| S-01 | 기본점수 = 창 안의 빈도 60% + 부정강도 40% |
| S-02 | 안전 관련 ×2.0 |
| S-03 | 급증 ×1.5 (최근 15분 유입률 ≥ 직전 60분 평균 × 2) |
| S-04 | 안전 3건 이상이면 점수와 무관하게 `immediate` |
| S-05 | 긍정은 심각도 계산에서 제외 |
| S-06 | 미조치 30분 경과 ×1.2 |

### 주요 기능

- **QR 접수**: 이름과 연락처를 받지 않는다. 구역과 민원 내용만 저장한다.
- **개인정보 보호**: 분류 저장소(`feedback`)에 넣기 전에 연락처, 주민번호, 카드번호, 이메일, 차량번호를 가린다. 웹으로 접수한 글은 접수함에 잠깐 머물고, 워커가 마스킹해서 옮긴 직후 접수함의 원문을 지운다. 민원 본문은 데이터로만 다루고, "이전 지시를 무시하라" 같은 인젝션 문구를 탐지해 무시한다.
- **조치요청서**: 담당 부서, 건수 요약, 원문 인용 5건, 조치 제안, 판정 계산식을 담은 DOCX를 만든다.
- **리플레이 엔진**: 시각이 기록된 민원을 배속으로 재생해, 며칠치 유입 속에서 순위가 바뀌는 과정을 검증한다.
- **외부 API**: 한국관광공사 TourAPI 4.0(`searchFestival2`, `detailCommon2`)을 도구로 연동했다. 실패하면 캐시, 수기 구역 시드 순으로 대체한다. [확인 필요: API 키 발급 여부]

### 백엔드 전환

`.env`의 `LLM_BACKEND` 한 줄로 에이전트의 두뇌를 바꾼다.

| 값 | 동작 | 용도 |
|---|---|---|
| `anthropic` | 실제 모델 (API 키) | 제출본 |
| `claude_code` | 실제 모델 (Claude Code CLI 경유) | 키 없이 실제 판단 확인, 개발용 |
| `local` | 규칙 기반 대역 | 개발·리허설 전용, 제출물 아님 |

`claude_code`는 API 키 없이 이 PC의 `claude -p`로 실제 모델 판단을 받는 개발용 경로다. 로그를 `cli_call`로 따로 남겨 제출 검증(`api_call`)과 섞이지 않게 했다. 세 경로는 같은 도구를 같은 순서로 호출한다. 대역은 제출물이 아니며, 코드 주석, 로그, README, 관리자 설명서, 관제 화면에 그렇게 표시했다.

### 개발 중 잡은 버그

실제로 발견하고 고친 버그가 여럿이다. 몇 가지를 적는다.

- 전화번호 마스킹 누락: 정규식 `\b`가 한글 앞에서 경계로 잡히지 않았다(TC5에서 발견).
- 두 순위가 다른 모집단을 비교: 건수는 누적, 심각도는 60분 창이었다.
- 조치요청서 저장 실패: 라벨 "안내/동선"의 `/`가 경로로 해석됐다.
- TC4가 대역에서 거짓 통과: API를 부르지 않으니 실패가 나지 않았다.
- ③조치 에이전트가 문서 생성을 멈춤: 요청문에 건수와 축제명이 빠져 있었다. 실제 모델 경로에서 발견했다.
- 조치요청서가 요청 후 4분 걸림: 배후 에이전트가 도는 동안 웹 요청이 막혔다. 요청 전용 스레드로 분리해 50초로 줄였다(실시간 테스트).
- 통합 에이전트가 한 번에 브리핑을 두 번 저장: 저장 도구를 부르면 실행이 끝나게 바꿨다. 모델 호출도 3회에서 2회로 줄었다.
- 조치 상태 오판: 같은 유형 요청서가 여럿이면 가장 오래된 상태를 읽었다. 실제 모델이 브리핑에서 "우선순위 계산 결과가 틀렸다"고 먼저 짚었다. 최신 상태를 읽게 고치고, 다시 만든 요청서는 이전 건을 `superseded`(대체됨)로 닫는다.
- 에이전트가 도는 동안 새 민원 접수·분류가 멈춤: 접수 뒤 약 1분 30초 동안 유입에 뜨지 않았다. 접수, 분류, 요청서, 에이전트를 각각 다른 스레드로 나눴다. 수정 뒤 유입 0.5초, 분류 20.5초(CLI 경유).
- 웹 API 서버 중복 실행: Windows에서 같은 포트가 두 번 열려 요청이 나뉘었다. 두 번째 실행을 거부하게 했다.

## 5. 성과

**E2E 관통.** 접수 → 분류 → 심각도 → 알림 → 조치요청서(DOCX) → 브리핑까지 전 구간이 한 줄로 이어진다. 대회가 요구하는 E2E 워크플로 1개 이상을 충족한다.

**심각도 역전 재현.** 개발용 합성 시드로 리플레이를 돌리면 건수 1위와 심각도 1위가 갈린다. 시드 전체를 넣고 심각도 창을 4일(5760분)로 잡은 기준이며, **분류는 AI 모델이 아니라 규칙 기반 대역(`local`)이 했다.** 아래 수치는 합성 시드·규칙 기반 대역 분류 기준이다. 주차/교통은 53건으로 건수 1위지만 심각도는 56.9점(3위)이다. 안전은 11건뿐인데 심각도 1위(93.2점)다. 2위는 혼잡 3건(70.4점)이다. 분류 신뢰도가 낮은 5건은 '확인 필요'로 빠져 집계에 없다. 안전 점수의 계산식은 아래와 같다.

`(0.08×60 + 0.85×40) × 안전2.0 × 급증1.0 × 미조치1.2 = 93.2`

위 계산식은 4일(5760분) 창 값이다(경계 규칙 B-01~B-04와 '확인 필요' 분리를 적용한 뒤 다시 계산). 창을 두지 않은 누적 분류 수로는 주차 54건이다. [확인 필요: 이 값은 규칙 기반 대역이 분류한 합성 시드 기준. 실제 모델·실제 시드로 재현] [확인 필요: 실제 수집 시드로 재현]

**실제 모델 동작 확인.** Claude Code CLI 경유로 에이전트 4종을 한 바퀴 돌렸다. ①은 인젝션 문장을 무시하고 신뢰도 0.1로 표시했고, ②는 도구를 7회 호출해 알림 3건을 냈다. ③은 인용 5건과 제안 3건을 담은 요청서를 만들었고, ④는 브리핑을 저장했다. 이어서 화면까지 켠 실시간 테스트도 통과했다(4절). API 키로 도는 제출 경로의 검증은 [확인 필요]다.

**처리 원가.** 민원 1건 처리 원가는 [확인 필요]다. CLI 경유 기록으로 낸 참고값(`원가측정_참고.md`)은 있지만 성과로 쓰지 않는다. CLI는 호출마다 자체 프롬프트가 붙어 API와 금액이 다르고, 시연용 20초 주기에 민원이 적어 1건당 값이 부풀었다.

**실사용자 검증.** [확인 필요: 3명 이상 피드백, 이름·소속, 검증일자]

## 6. 한계

- **데이터**: 현재 리플레이 시드(`seed/dev_sample.csv`, 160건)는 개발용 합성 데이터다. 실제 수집 데이터가 아니다. 위 역전 수치도 합성 데이터 기준이다. [확인 필요: 실제 수집 시드 교체 여부와 건수·출처]
- **정확도 근거 부족**: 실제 모델 정확도가 아직 없다. 대역 수치는 성과가 아니고, CLI 경유 수치(32/32)는 합성 표본 32건이라 95% 신뢰구간이 89.3~100%로 넓고 안전 정답은 4건뿐이다(안전 재현율 신뢰구간 51~100%).
- **Test Case**: 현재 기록은 구조 검증 모드다. 실제 모델 호출을 포함한 결과가 필요하다.
- **운영 데이터 문제**: 실제 모델이 짚은 문제가 있다. 같은 문장이 1초 간격으로 여러 구역에서 중복 접수됐다. (브리핑 두 번 저장은 고쳤다.)
- **실제 모델 검증 경로**: 실시간 테스트는 Claude Code CLI 경유로 했다. API 키 경로의 재검증과 Streamlit 화면의 실제 모델 조작이 남아 있다.
- **범위**: 상용 수준의 보안과 대규모 운영은 범위 밖이다(대회 Level 3 MVP 기준).
- **현장 검증 부재**: 실제 축제 기간에 운영한 적은 없다. 리플레이로 대신 검증했다.

기존 자산을 가져다 붙인 것이 아니라 팀이 새로 만든 부분이다.

- 조치요청서 DOCX 생성 (원문 인용, 판정 근거 포함)
- 개인정보 마스킹과 프롬프트 인젝션 탐지
- 리플레이 엔진
- 백엔드 전환 구조 (실제 모델 / CLI 경유 / 개발용 대역), CLI 경유 경로의 도구 호출 루프

- Supabase 전환 구조와 local 대역 API 서버, 웹 앱
