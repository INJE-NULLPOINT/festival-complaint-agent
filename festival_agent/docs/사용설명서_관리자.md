## 1. 시스템 개요

방문객이 축제장 QR로 불편을 제출하면 초 단위로 분류하고, 무엇을 먼저 조치해야
하는지 판단해, 담당 부서용 조치요청서까지 생성합니다.

이 시스템은 건수 순서가 아니라 심각도 순서로 판단합니다.

예시 (개발용 합성 시드를 4일 구간으로 재생하고 **규칙 기반 대역이 분류**했을 때 — 실제 축제 통계나 AI 모델 분류 결과가 아닙니다. 분류 신뢰도가 낮은 민원은 '확인 필요'로 빠져 순위에 들어가지 않습니다):

| 유형 | 건수 | 이 시스템의 순위 |
|---|---|---|
| 주차/교통 | 53건 (건수 1위) | 3위 |
| 안전 | 11건 | **1위** |
| 혼잡 | 3건 | 2위 |

안전이 위로 올라가는 이유는 안전 관련 민원에 ×2.0 가중이 붙고, 3건 이상이면 점수와
무관하게 즉시 조치 등급이 되기 때문입니다.
건수에 묻혀 사라지던 안전 신호를 드러내는 것이 이 시스템의 목적입니다.

## 2. 설치와 준비

### 2.1 설치

Node 24 이상이 필요합니다 (서버는 TypeScript, 빌드 없이 실행). 명령은 `festival_agent/` 에서 칩니다.

```bash
npm install --prefix server
```

### 2.2 API 키

`.env.example`을 `.env`로 복사한 뒤 값을 채웁니다.

```
ANTHROPIC_API_KEY=sk-ant-...
TOURAPI_KEY=
```

| 키 | 용도 | 필수 여부 |
|---|---|---|
| `ANTHROPIC_API_KEY` | 분류·판정·문서작성 | 운영·제출(`LLM_BACKEND=anthropic`)에는 필수. `claude_code` 로 개발할 때는 없어도 됨 |
| `LLM_BACKEND` | 에이전트 두뇌 선택 (2.3 참조) | 선택. 비워 두면 API 키 유무로 자동 판단 |
| `ADMIN_CODE` | 운영자 코드 — 민원 지우기·조치 상태 변경·요청서 생성을 열어 주는 열쇠 | 운영에는 필수. 비우면 그 동작이 전부 잠김. 값은 직접 정해 여기에만 넣기 |
| `TOURAPI_KEY` | 한국관광공사 축제 공식정보 조회 | 선택 |

TourAPI 키는 data.go.kr에서 "한국관광공사_국문 관광정보 서비스_GW"를 활용신청한 뒤,
마이페이지 > 개발계정 > 일반 인증키(Decoding)를 복사합니다. 없어도 시스템은 정상
동작합니다.

`.env` 파일은 저장소에 올리지 마십시오. `.gitignore`에 등록돼 있습니다.

### 2.3 백엔드 확인

에이전트가 실제 모델로 도는지 개발용 대역으로 도는지 확인합니다.

```bash
node server/cli.ts check
```

| 표시 | 의미 |
|---|---|
| 백엔드 anthropic | 실제 모델이 판단합니다. 운영·제출 상태입니다 |
| 백엔드 claude_code | 실제 모델이 판단합니다. 이 PC의 Claude Code CLI를 거칩니다. API 키 없이 실제 판단을 확인하는 개발용이며 구독 사용량을 씁니다 |
| 백엔드 local | 규칙 기반 대역입니다. 개발용이며 운영에 쓰면 안 됩니다 |

`.env`의 `LLM_BACKEND`로 전환하며, 미지정이면 API 키 유무로 자동 판단합니다
(`claude_code`는 직접 지정해야 합니다).
현재 백엔드는 웹 화면 맨 위의 AI 배지(`AI: Claude API` / `AI: Claude Code (개발용)` / `AI: 규칙(개발용)`)로 보입니다(4.2).
그 옆의 `실시간 · 로컬 DB` / `실시간 · Supabase`는 에이전트 두뇌가 아니라 **데이터 연결**입니다.
운영은 Supabase에 연결돼 있어 `실시간 · Supabase`로 보입니다(2026-09-30 연결). `로컬 DB`로 보이면 개발·테스트용 `webapi.ts`(SQLite)에 붙은 것입니다.

### 2.4 축제 정보 설정

```bash
node server/scripts/seed_festival.ts --list      # 경남 축제 목록
node server/scripts/seed_festival.ts --pick 유등  # 대상 축제 설정
```

TourAPI 키가 없으면 `server/core/config.ts`의 기본값이 쓰입니다.

## 3. 실행

화면은 **웹 화면** 하나입니다(Vite + TypeScript). 개발계획서에 적었던 Streamlit 화면은 2026-10-01에 뺐습니다.
웹 화면이 돌려면 에이전트 워커와 데이터 API가 함께 떠 있어야 합니다.

### 한 번에 켜기 (권장)

```bash
node server/scripts/run_all_servers.ts          # webapi(8765) + worker + 웹(5173). 죽으면 다시 띄우고 30분마다 DB 백업
node server/scripts/run_all_servers.ts --phone  # 웹 대신 폰 확인용 빌드본(4173)
```

### 따로 켜기 — 터미널 3개

```bash
node server/worker.ts                 # 터미널 1 — 에이전트 워커
node server/webapi.ts                 # 터미널 2 — 데이터 API (127.0.0.1:8765)
cd web && npm install && npm run dev   # 터미널 3 — http://localhost:5173
```

| 주소 | 화면 |
|---|---|
| `/#control` | 관제 (기본) |
| `/#action` | 조치 |
| `/#report` | 접수 (운영자 확인용) |
| `/?v=qr` | 방문객 접수 화면. 상단 탭이 숨겨집니다. QR이 여는 주소입니다 |

같은 Wi-Fi의 휴대폰에서 열려면 `npm run dev -- --host`로 켜고 PC의 주소를 씁니다.
`webapi.ts`를 두 번 켜면 두 번째는 "이미 실행 중"이라며 종료됩니다.
지금 웹은 `web/.env`의 Supabase 설정으로 Supabase에 직접 붙습니다(이때 `webapi.ts`는 쓰지 않음). 연결 방법은 README의 '웹 앱' 절을 보세요.

### 에이전트 워커

```bash
node server/worker.ts
```

| 명령 | 동작 |
|---|---|
| `node server/worker.ts` | 분류 3초 주기, 에이전트 60초 주기 |
| `node server/worker.ts --agent-interval 20` | 시연용. 반응을 빠르게 |
| `node server/worker.ts --no-agents` | 분류만 실행. 비용 절약 |

워커는 접수 수거, 분류, 조치요청서 요청, 에이전트 실행을 따로 처리합니다.
에이전트가 한 바퀴 도는 데 오래 걸려도 새 접수와 요청서 요청은 밀리지 않습니다.

워커를 끄면 민원이 접수만 되고 분류되지 않습니다. 관제 화면의 "분류 대기" 숫자가
계속 올라가면 워커가 꺼진 것입니다.

## 4. 화면별 사용법

### 4.1 접수 화면

축제장 구역마다 이 화면의 QR을 붙입니다. 주소 뒤에 구역 번호나 이름을 붙이면 해당
구역이 미리 선택된 채로 열립니다. 방문객에게 보이는 화면과 안내는 `사용설명서_이용자.md`를
보세요.

```
http://<서버주소>:5173/?v=qr&zone=4          (구역 번호)
http://<서버주소>:5173/?v=qr&zone=유등터널    (구역 이름)
```

QR은 관리자 화면의 **'접수 QR'(QR 만들기)** 에서 만듭니다. 방문객 폰이 열 수 있는 기본 주소
(공개 주소, 또는 같은 Wi-Fi의 PC 주소)를 넣으면 접수 화면(`?v=qr`) QR 한 장이 바로 그려지고,
**인쇄**를 누르면 A4 한 장에 크게 나옵니다. 구역은 QR로 정하지 않고 방문객이 화면에서 고릅니다.
주소가 `localhost`면 폰에서 열리지 않는다는 경고가 뜹니다. PC 주소가 바뀌면 새 주소로 다시 인쇄합니다.
구역 목록은 `server/core/config.ts`의 `ZONES`에서 수정합니다.


### 4.2 관제 화면

운영 요원이 띄워 두는 화면입니다. 흑백 톤이고, 등급 배지와 카드 왼쪽 띠에만 색이 있습니다.
변경이 생기면 실시간으로 다시 그려집니다. 위에서부터 순서대로 봅니다.

**맨 위 배지 (데이터 · AI · 합성)**
화면 맨 위 제목 옆에 작은 배지가 붙습니다.

| 배지 | 뜻 |
|---|---|
| `실시간 · 로컬 DB` / `실시간 · Supabase` | 데이터가 어디에 연결됐는지. 연결이 끊기면 `재연결 중`으로 바뀝니다 |
| `AI: Claude API` / `AI: Claude Code (개발용)` / `AI: 규칙(개발용)` | 에이전트가 무엇으로 판단하고 있는지. `규칙(개발용)`은 규칙 기반 대역이라 운영에 쓰면 안 됩니다 |
| `합성 데이터 포함 · N건` | 개발용 합성 민원이 섞여 있을 때만 나옵니다. 시연·보고에 쓰는 화면이면 이 사실을 함께 밝히십시오 |

방문객 화면에는 이 배지가 없습니다. Supabase 로 연결했을 때는 AI 배지가 나오지 않습니다(서버가 AI 방식을 알려 주지 않음).

**지금 조치할 일 (브리핑)**
지금 무엇을 먼저 해야 하는지 한 문단으로 알려줍니다. 첫 문장이 결론이라 굵게 보이고, 아래에 `근거:` 한 줄이 붙습니다.
워커가 에이전트를 한 바퀴 돌기 전에는 `워커가 에이전트를 한 바퀴 돌면 표시됩니다.`가 나옵니다.

**조치할 일 카드**
브리핑 바로 아래에 카드가 순서대로 놓입니다. 1번 카드가 가장 크고, 나머지는 한 줄씩입니다.
그 아래 `그 밖 N건` · `조치 중 N건` · `조치 완료 N건`이 접혀 있습니다. 카드 읽는 법은 4.4를 보세요.
조치할 카드가 없으면 `지금 바로 조치할 일은 없습니다.`가 나옵니다.

**알림**
카드 아래에 확인하지 않은 알림이 한 줄씩 나옵니다(급증, 안전 임계 초과, 등급 상승, 안전 의심 확인 필요 방치 등).
배지, 내용, 시각 순입니다.

**유형별 순위 (접혀 있음)**
`유형별 순위 · 카드 순서의 근거`를 누르면 펼쳐집니다. 유형 단위 심각도 1위와 그다음 순위, 각 유형의 건수 순위가 보입니다.
건수 1위와 심각도 1위가 다르면 이런 문구가 나옵니다.

> 건수 1위 주차/교통 53건보다 안전 11건이 먼저입니다

(위 문구의 숫자는 1절 표와 같은 예시입니다 — 개발용 합성 시드 · 4일 구간 · 규칙 기반 대역 분류 기준.)

순위는 내부 점수로 정해지지만 **점수 숫자와 계산식은 화면에 보이지 않습니다.** 화면에는 등급 배지(즉시·높음·보통·낮음)와 건수만 나옵니다.
이 점수는 AI가 생성한 값이 아니라 고정된 계산식의 결과라서, 같은 상황이면 항상 같은 순서가 나옵니다.

**실시간 유입**
방금 들어온 민원이 원문 한 줄과 함께 보입니다. 유형, 구역, 시각은 아래에 따로 적히고,
상태에 따라 유형 대신 `분류 중` · `확인 필요` · `유형 없음`이 나옵니다. 방문객 화면에서 들어온 민원에는
방문객이 받은 것과 같은 접수번호(`W-43` 같은 번호)가 붙습니다. 구역을 알 수 없는 민원은 `구역 미상`으로 나옵니다.

제목 옆에 `누적 N · 분류 대기 N · 확인 필요 N · 안전 의심 N · 지운 민원 N`이 있습니다.
`확인 필요`를 누르면 확인 필요 처리 패널이 열립니다(4.4). 행마다 휴지통 버튼이 있어 민원을 지울 수 있습니다(4.4).

**에이전트 활동 로그**
웹 관제 화면에는 없습니다. 어떤 에이전트가 어떤 도구를 언제 사용했는지는 다음 명령이나
워커 로그(`output/logs/worker.log`, `run_all_servers.ts`로 켰을 때)로 봅니다. 문제가 생기면 여기부터 확인합니다.

```bash
node server/cli.ts db log
```

심각도 구간(창)은 화면에서 바꾸지 않고 워커를 켤 때 정합니다(`node server/worker.ts --window 60`, 기본 60분). 건수 순위와 심각도 순위는 같은 구간을 봅니다.

### 4.3 조치 화면

**조치 대상**은 심각도 순입니다. 유형마다 등급 배지, 건수가 보이고 오른쪽에 버튼이
있습니다.

- `조치요청서 생성` — 처음 만들 때. 즉시·높음 등급이면 검게 강조됩니다
- `다시 생성` — 아직 끝나지 않은 요청서가 이미 있을 때. 강조되지 않습니다

누르면 요청이 워커로 넘어가고, 유형 아래에 상태가 나옵니다.

| 표시 | 뜻 |
|---|---|
| 대기 중… | 워커가 아직 집지 않았습니다 |
| 작성 중… | 조치 에이전트가 문서를 만들고 있습니다. 수십 초 걸릴 수 있습니다 |
| 실패: … | 만들지 못했습니다. 이유가 함께 나옵니다 |
| 요청서 발송됨 | 끝나지 않은 요청서가 있습니다 |

워커가 꺼져 있으면 `대기 중…`에서 넘어가지 않습니다.
생성되는 조치요청서에는 다음이 포함됩니다.

- 민원 유형, 건수, 심각도, 판정 근거 계산식
- 민원 원문 인용 5건 (구역·시각 포함)
- 즉시 실행 가능한 조치 제안 2~3개

**조치요청서 · 처리 현황**에서 상태를 `요청 → 조치중 → 완료`로 바꿉니다.
흑백에서도 구분되도록 상태마다 모양이 붙습니다: ● 요청, ◐ 조치중, ✓ 완료.
`미리보기`로 문서 내용을 화면에서 확인하고, `DOCX` 버튼으로 문서를 내려받아 부서에
전달합니다.

같은 유형의 요청서를 `다시 생성`하면 이전에 열려 있던 요청서(요청·조치중)는
`대체됨`이 되어 목록에서 접힙니다. 아래 `대체된 요청서 N건 보기`를 누르면 볼 수 있고,
대체된 요청서는 상태를 바꿀 수 없습니다. 완료된 요청서는 그대로 남습니다.

상태 변경은 기록용이 아닙니다. 30분이 지나도 조치되지 않으면 심각도에 1.2배 가중이
붙고 통합 에이전트가 우선순위를 다시 매깁니다. 통합 에이전트는 같은 유형의 요청서가
여러 개면 가장 최근 요청서의 상태를 봅니다. 실제로 조치했을 때만 완료로
바꾸십시오.

### 4.4 지금 조치할 일 카드와 민원 지우기

**카드 한 장의 모양** (1번 카드 기준, 위에서 아래로)

1. 번호와 `지금 가장 먼저 · HH:MM 기준`
2. **문제 한 줄**(굵게) — 예: `유등터널 입구에 인파가 몰려 밀림`
3. 구역 · 유형 아이콘과 이름 · 등급 배지 · `N건 · 마지막 HH:MM` · 표시(`같은 구역 다른 문제 N` 등)
4. **해야 할 일** — 번호 붙은 조치 목록, 조치마다 오른쪽에 `근거 #번호`. 고위험 조치가 있으면 그 아래
   `⚠ 운영자 판단 필요 — 실행 전 현장 확인` 칸에 **따로** 나옵니다(일반 조치와 섞이지 않음)
5. `담당 부서 · 연락처`
6. 두 묶음: **판단 근거** — 문구가 근거로 든 민원 / **최신 민원**(`실시간`) — 방금 들어온 민원. 최신 민원 행에는 휴지통이 있습니다
7. 버튼: `{유형} 전체 요청서 생성`(이미 있으면 `다시 생성`) · 요청서 상태 · `조치 화면에서 상태 바꾸기`
8. 맨 아래 작은 글씨: AI가 쓴 문구인 카드에만 `AI 정리 · HH:MM`이 붙습니다

2번째 카드부터는 문제 한 줄과 3번 줄만 보이는 한 줄 카드이고, 누르면 펼쳐집니다.

관제는 유형 순위만 보여 주지 않고, **"지금 무엇을, 어디서, 무엇부터, 어떻게"** 를 카드 한 장씩 보여 줍니다.
카드 하나는 **유형 × 구역** 입니다. 같은 구역에서 혼잡과 안전이 함께 들어오면 카드가 두 장이고,
각 카드에 `같은 구역 다른 문제 1` 처럼 표시됩니다. 구역을 알 수 없는 민원은 `구역 미상` 카드 한 장으로 모입니다.

**카드에 보이는 것**

| 항목 | 누가 정하나 | 내용 |
|---|---|---|
| 문제 한 줄 | AI | 근거 민원을 읽고 정리한 한 줄 (40자 이하) |
| 해야 할 일 2~4개 | AI | 운영자가 오늘 현장에서 할 구체적인 행동. 조치마다 **근거 민원 1건**이 붙어 있음 |
| 등급 | 코드 | 등급은 유형 등급 그대로. 카드 순서에는 내부 점수(유형 심각도 × 집중 × 최근)를 쓰지만 화면에는 보이지 않음 |
| 건수 · 마지막 민원 시각 · 최신 민원 | 코드 | LLM 없이 몇 초마다 바로 갱신 |
| 담당 부서 · 연락처 | 코드 | `DEPARTMENT_MAP` 그대로 |
| 표시 | 코드 | `운영자 판단 필요`, `완료 후 재발`, `요청서 이후 새 구역`, `같은 구역 다른 문제 N` |

- **`운영자 판단 필요`** — 조치에 중단·폐쇄·대피·진입 통제·출입 통제·출동·경찰·소방 같은 고위험 표현이 들어간 카드입니다.
  이런 표현은 안전 유형이면서 즉시 등급인 카드에서만 나오고, 실행 여부는 반드시 운영자가 정합니다.
  "통제선 설치", "통제 요원 배치" 같은 평범한 조치는 해당하지 않습니다. 안전 카드의 판단 필요 조치는 다른 조치와 구분해서 보는 것이 좋습니다.
- **`요청서 이후 새 구역`** — 요청서는 유형 단위라서, 이미 `조치 중`인 유형에 **다른 구역에서 새로** 민원이 생기면 그 카드는
  `조치 중`으로 접지 않고 본 목록에 남겨 이 표시를 붙입니다 (새 구역의 문제가 묻히지 않게).
- **문구의 근거와 최신 민원은 따로입니다.** 근거 인용은 AI가 문구를 다시 쓸 때만 바뀌고, 최신 민원은 계속 바뀝니다.
  문구가 실제로 바뀐 카드만 강조됩니다.

**순서와 그룹**

1. 조치 그룹 — 본 목록(요청서 없음·요청) → 조치 중 → 조치 완료. 완료한 유형에 새 민원이 들어오면 본 목록으로 돌아오고 `완료 후 재발`이,
   조치 중인 유형의 새 구역 카드는 본 목록에 남고 `요청서 이후 새 구역`이 붙습니다.
2. 등급 — 즉시 > 높음 > 보통 > 낮음
3. 안전 계열(안전·혼잡)이 먼저 — 같은 등급이면 점수와 상관없이 안전·혼잡이 앞입니다.
4. 내부 카드 점수(화면에는 보이지 않음), 마지막 민원 시각 순

본 목록은 상위 5장이고 나머지는 `그 밖`으로 접힙니다. 카드가 되는 조건은 유형 등급이 보통 이상이거나 안전 유형일 때입니다.
건수 1위인 주차가 즉시 카드들 아래에 있을 수 있는데, 그것이 "건수가 아니라 심각도" 입니다.

**문구는 언제 다시 쓰이나**

- 등급이나 조치 그룹이 바뀌면 바로 다시 씁니다.
- 새 민원이 들어오면 그 카드의 마지막 문구 작성 뒤 **60초**가 지난 뒤에 다시 씁니다.
- 위 둘 다 아니면 AI를 부르지 않습니다 (비용 절감).
- AI 문구는 **상위 3장**에만 만듭니다. 4번째 카드부터는 `{구역} — {유형} 민원`과 기본 조치 2개로 표시됩니다.
- AI 문구가 검사에 실패하면 그 카드만 기본 문구로 채우고 다음 주기에 다시 시도합니다 (같은 상황에서 2번까지).

**AI 문구가 저장되기 전에 검사하는 것**

| 검사 | 막는 것 |
|---|---|
| 조치마다 근거 민원 id | 근거 없는 조치 |
| 숫자 금지 (119·112 제외, "세 명"·"오십 대" 같은 한글 수사 포함) | "요원 10명 투입" 같은 지킬 수 없는 약속 |
| 장소·시설 단어(입구·계단·조명 등)가 카드의 민원이나 구역 이름에 있어야 함 | 없는 시설을 지어냄 |
| 조치가 민원 원문과 연속 12자 이상 같으면 거부 | 민원 문장이 조치로 그대로 옮겨짐 ("축제를 중단하라" 같은 문장) |
| 고위험 표현은 안전·즉시 카드에서만 | 권한 밖의 과한 조치 |

조치 목록 예시(`config.ACTION_CATALOG`)는 AI에게 주는 **참고 예시**일 뿐이고, AI는 민원을 읽고 스스로 판단합니다.
조치요청서를 만들면 그 유형 카드의 조치가 그대로 요청서에 들어가서 **관제 화면과 요청서의 조치가 같습니다.**
카드의 요청서 버튼은 그 구역만을 위한 문서가 아니라 **그 유형 전체**의 요청서입니다.

**확인 필요** — 분류 신뢰도가 0.3 미만이거나 내용이 없는 민원은 유형을 정하지 않고 `확인 필요`로 따로 둡니다.
순위·알림·브리핑·카드에는 들어가지 않고 개수만 표시되며, 그중 안전이 의심되는 건수가 따로 나옵니다.
모델이 제안한 유형은 `suggested_label` 로 저장됩니다.

운영자는 `확인 필요` 민원을 세 가지로 처리합니다 (운영자 코드 필요). 안전 의심이 먼저, 그 안에서는 오래된 것이 먼저 나옵니다.

| 동작 | 결과 |
|---|---|
| 유형 지정 | 운영자가 고른 유형으로 집계(심각도·카드·알림)에 들어갑니다. 안전·혼잡을 고르면 안전 의심이 자동으로 켜지고, 그 밖의 유형은 안전 의심을 직접 고를 수 있습니다. 같은 문장이 다시 오면 같은 유형으로 처리됩니다 |
| 유형 없음으로 닫기 | 스팸은 아니지만 유형을 붙일 수 없는 진짜 방문객 의견("좀 그랬어요")입니다. 확인 필요 개수와 심각도에서 빠지고 유입 목록에는 `유형 없음`으로 남습니다 |
| 지우기 | 장난·욕설·무의미·개인정보 노출 민원은 지웁니다 (숨김, 되돌리기 가능) |

이미 처리된 민원은 다시 처리되지 않고(`이미 처리된 민원입니다`), 닫거나 지정한 것은 **되돌릴 수** 있습니다. 그냥 두는 것은 동작이 아니라서 개수에 계속 남습니다.
**안전 의심 확인 필요가 15분 넘게 처리되지 않으면 알림이 한 번 올라갑니다** (같은 민원은 한 번만). 운영자가 처리한 민원은 분류 정확도 계산에서 모델 정답으로 치지 않고 제외합니다.

**민원 지우기 (숨김)** — `...` 처럼 쓸모없는 민원은 운영자가 한 건씩 지울 수 있습니다.

- 지우면 행을 삭제하지 않고 **숨김 처리**만 합니다. 기록은 남고, 바로 **되돌릴 수 있습니다.**
- 지운 민원은 건수·심각도·알림·브리핑·조치요청서 인용·카드·분류 대기열·실시간 유입 **어디에도 나오지 않습니다.**
  되돌리면 모두 원래대로 돌아옵니다.
- **지우는 법** — 실시간 유입의 각 행, 카드의 `최신 민원` 행, 확인 필요 패널의 `지우기` 버튼. 휴지통을 누르면 바로 사라지고
  화면 아래에 `지웠습니다 · 되돌리기`가 10초 동안 뜹니다(마우스를 올리거나 키보드 포커스가 있는 동안은 멈추고, 놓으면 적어도 3초는 더 보임). 운영자 코드가 필요합니다(아직 입력 전이면 코드 창이 먼저 뜨고, 입력하면 이어서 지워짐).
- **되돌리기는 그 안내가 떠 있는 동안에만** 화면에서 할 수 있습니다. 지운 개수는 실시간 유입 제목 옆 `지운 민원 N`으로 보이지만, 그 숫자를 눌러 되살리는 기능은 없습니다.
  안내가 사라진 뒤 되살리려면 `restore_feedback` 호출(개발자)이 필요합니다.
- 지운 민원이 카드의 근거 인용으로 쓰이고 있었다면 그 인용도 바로 빠지고, 문구는 다음에 다시 쓸 때 고쳐집니다.
- 방문객 화면에는 지우기가 없습니다.

### 4.5 운영자 코드 창

민원 지우기 · 조치 상태 변경 · 조치요청서 생성 · 확인 필요 처리는 운영자만 할 수 있습니다.
이 동작을 처음 누르면 `운영자 코드` 창이 뜹니다. 방문객 화면에는 이 창과 관리자 버튼이 없습니다.

- 코드는 `.env`의 `ADMIN_CODE`(2.2)에 정한 값입니다. `보기`를 누르면 입력한 글자가 보입니다.
- 맞으면 누른 동작이 이어서 실행되고, **그 브라우저 탭을 닫을 때까지** 다시 묻지 않습니다.
- 창에 나오는 안내

| 문구 | 뜻 |
|---|---|
| `코드가 맞지 않습니다. 다시 입력해 주세요` | 틀렸습니다 |
| `저장된 코드가 더 이상 맞지 않습니다. 다시 입력해 주세요` | 서버의 코드가 바뀌었습니다 |
| `서버에 운영자 코드가 설정되지 않았습니다. 운영자에게 알려 주세요` | `ADMIN_CODE`가 비어 있어 관리자 동작이 전부 잠겨 있습니다 |
| `시도가 너무 많습니다. 잠시 후 다시 시도해 주세요 (약 10분)` | 10분 안에 5번 틀려 잠겼습니다. 잠긴 동안에는 맞는 코드도 거부됩니다 |
| `운영자 코드 입력을 취소했습니다` | `취소`를 눌렀습니다. 누른 동작은 실행되지 않습니다 |

주의: 틀린 시도는 사용자별이 아니라 전체로 셉니다. 같은 서버에 접속한 누군가가 틀린 코드를 5번 보내면 운영자도 10분 동안 막힐 수 있습니다
(할일 D5-40 ①, 아직 고치지 않음). 폰 시연처럼 서버를 같은 와이파이에 열 때는 이 점을 알고 쓰십시오.

## 5. 심각도 판정 규칙

| ID | 규칙 |
|---|---|
| S-01 | 기본점수 = 최근 구간 빈도 60% + 불만 강도 40% |
| S-02 | 안전 관련이면 ×2.0 |
| S-03 | 최근 15분 유입이 평소의 2배 이상이면 급증 ×1.5 |
| S-04 | 안전 민원 3건 이상이면 점수와 무관하게 즉시 조치 등급 |
| S-05 | 긍정(칭찬)은 심각도 계산에서 제외 |
| S-06 | 조치 없이 30분 경과 시 ×1.2 |

등급 구간은 다음과 같습니다.

| 등급 | 점수 | 웹 배지 |
|---|---|---|
| 즉시 조치 | 80 이상 | 즉시 |
| 높음 | 60 이상 | 높음 |
| 보통 | 40 이상 | 보통 |
| 낮음 | 40 미만 | 낮음 |

한가한 시간에 민원 1건이 100점·즉시가 되지 않도록 **경계 규칙**이 함께 적용됩니다.

| ID | 규칙 |
|---|---|
| B-01 | 빈도 비율은 (창 전체 건수가 10건보다 적어도) 10건을 기준으로 계산 |
| B-02 | 급증은 최근 15분에 3건 이상일 때만 |
| B-03 | 안전 계열이 아닌 유형은 5건 미만이면 점수를 79.9 로 제한 (최고 `높음`). 계산식 끝에 표시됨 |
| B-04 | 안전·혼잡은 1건이라도 점수 하한 60 (최소 `높음`). S-04 는 그대로 |

기준값은 `server/core/config.ts` 상단에서 수정할 수 있으며, 변경 시점부터 적용됩니다.

## 6. 리플레이

과거 민원을 타임스탬프 순서대로 배속 재생합니다. 명령으로 시작합니다(웹 화면에는 시작 버튼이 없습니다).

```bash
node server/cli.ts replay start --speed 300
node server/cli.ts replay stop
```
 며칠치 민원이 몇 분 만에 흐르면서 심각도 순위가 변하는
과정을 확인할 수 있습니다.

개발 중 검증과 시연 리허설에 사용합니다.

```bash
node server/scripts/make_dev_seed.ts    # 개발용 샘플 생성
```

`seed/dev_sample.csv`는 개발용 합성 데이터이며 실제 방문객이 작성한 글이 아닙니다.
실제 운영에서는 직접 수집·정제한 데이터로 교체하십시오.

## 7. 다른 축제로 이관

코드 수정 없이 `server/core/config.ts` 세 곳만 변경하면 됩니다.

| 항목 | 내용 |
|---|---|
| `FESTIVAL` | 축제 이름, 지역, 기간 |
| `ZONES` | 구역 목록 (QR 단위) |
| `DEPARTMENT_MAP` | 민원 유형 → 담당 부서·연락처 |

분류 유형 자체를 바꾸려면 `LABELS`와 `SAFETY_LABELS`도 함께 수정합니다.
변경 후에는 `festival.db` 파일을 삭제하고 새로 시작하는 것이 안전합니다.

## 8. 문제 해결

| 증상 | 원인과 조치 |
|---|---|
| 분류 대기가 계속 쌓임 | 워커가 꺼졌습니다. `node server/worker.ts` 재실행 |
| 브리핑이 표시되지 않음 | `--no-agents`로 실행 중이거나 에이전트 주기가 아직 안 됐습니다. 60초 대기하거나 `--agent-interval 20` |
| 민원은 들어오는데 분류 안 됨 | API 키를 확인하고, 에이전트 활동 로그에서 오류를 확인합니다 |
| 조치요청서가 `대기 중…`에서 안 넘어감 | 워커가 꺼졌습니다. `node server/worker.ts` 를 다시 켜면 이어서 만듭니다 |
| 웹 화면에 "불러오지 못했습니다" | `node server/webapi.ts` 가 꺼졌습니다. 다시 켭니다 |
| `webapi.ts` 가 "이미 실행 중"이라며 종료됨 | 정상입니다. 같은 포트를 이미 쓰는 프로세스가 있습니다 |
| 카드 문구가 `{구역} — {유형} 민원` 으로만 보임 | 상위 3장 밖이거나, AI 문구가 검사에 실패했거나, 아직 첫 생성 전입니다. 다음 주기에 다시 시도합니다. 계속 그러면 에이전트 활동 로그의 `issue_check_failed` 사유를 봅니다 |
| 새 민원이 들어왔는데 카드 문구가 그대로 | 문구는 카드마다 마지막 작성 뒤 60초가 지나야 다시 쓰입니다. 건수·최신 민원은 바로 바뀝니다 |
| 민원이 집계에서 사라짐 | 누군가 지운(숨긴) 민원일 수 있습니다. 지운 개수를 확인하고 되돌립니다 |
| 민원이 `확인 필요`로만 보임 | 분류 신뢰도가 낮거나 내용이 없어 유형을 정하지 않았습니다. 내용을 확인해 지우거나 그대로 둡니다 |
| 지우기·조치 상태 변경·요청서 생성이 "운영자 코드가 필요합니다"로 거부됨 | 코드를 입력하지 않았거나 틀렸습니다. `.env` 의 `ADMIN_CODE` 가 비어 있어도 전부 거부됩니다. 10분에 5번 틀리면 10분 동안 잠깁니다 |
| 요청서 생성 실패 | `output/` 폴더 쓰기 권한을 확인하고 로그의 `dispatcher` 항목을 봅니다 |
| 축제 정보가 표시되지 않음 | `TOURAPI_KEY` 미설정입니다. 없어도 정상 동작하므로 무시해도 됩니다 |
| 화면 갱신 시 상태가 초기화됨 | 정상입니다. 화면은 상태를 보유하지 않고 매번 DB에서 다시 읽습니다 |
| API 호출이 실패함 | 민원은 대기열에 남고 워커가 다음 주기에 재시도합니다. 데이터는 유실되지 않습니다 |

로그는 워커 터미널 출력(또는 `output/logs/`)과 `node server/cli.ts db log`에서 확인합니다 (웹 관제 화면에는 활동 로그가 없습니다).

## 9. 비용 관리

변동비는 AI 호출 비용 하나입니다. 세 가지 절감 장치가 적용돼 있습니다.

1. 2경로 분리 — 접수·분류는 3초 주기, 판정·문서작성은 60초 주기
2. 새 민원이 없으면 에이전트를 실행하지 않음
3. 분류 캐시 — 같은 문장은 두 번 호출하지 않음 (리플레이에서 효과가 큼)

추가로 줄이려면 `--agent-interval`을 늘리거나 `server/core/config.ts`의 `MODEL`을 더 가벼운
모델로 변경합니다. 다만 통합 에이전트는 결론을 내리는 자리이므로 성능을 낮추지 않는
편이 좋습니다.

## 10. 개인정보와 안전

- 접수 화면은 이름과 연락처를 수집하지 않습니다. 구역과 민원 내용만 저장합니다.
- 본문에 연락처, 주민번호, 이메일, 카드번호, 차량번호가 **정해진 형식으로** 포함되면 저장 전에 자동
  마스킹됩니다. 형식이 없는 개인정보(이름, 주소, 형식을 벗어난 번호 표기 등)는 가리지 못합니다. 웹으로 접수한 글은 워커가 가져가기 전까지 접수함(`feedback_inbox`)에
  원문 그대로 잠깐 머뭅니다. 워커가 마스킹해서 옮긴 뒤 접수함의 원문은 지웁니다.
  그러니 워커를 꺼 두는 동안에는 원문이 접수함에 남아 있습니다.
- 민원 본문에 "이전 지시를 무시하라" 같은 문구가 있어도 에이전트는 이를 지시로
  취급하지 않습니다.
- **접수 도배 방지** (D5-33). 양으로는 막지 않습니다. 한 구역에 민원이 몰리는 것 자체가 위험 신호이기 때문입니다.
  - **같은 글 합치기:** 같은 구역에 같은 글이 **2분 안에** 다시 들어오면 새로 넣지 않고 앞의 접수에 합칩니다.
    - 같은 글인지는 개인정보를 가린 뒤 공백·기호를 빼고 영문을 소문자로 바꿔 비교합니다.
    - 보낸 사람에게는 앞 접수와 같은 접수번호로 성공 안내가 나갑니다. 합친 횟수는 `dup_count`에 남습니다.
    - 다른 사람이 글자까지 똑같이 쓴 경우도 2분 안이면 합쳐집니다. 말이 조금이라도 다르면 각각 들어갑니다.
  - **한 출처의 폭주 거절:** 한 접속 주소에서 **1분 10건 또는 10분 30건**을 넘으면 `잠시 후 다시 보내 주세요`로 거절합니다(한도는 방문객에게 알리지 않음).
    - 축제 와이파이처럼 여러 사람이 한 주소를 쓸 수 있어 한도를 넉넉하게 잡았습니다. 숫자는 설계값이라 리허설로 조정합니다(`config.SUBMIT_LIMITS`).
    - 접속 주소를 알 수 없으면 이 제한은 건너뜁니다.
  - **접속 주소 처리:** 원래 주소(IP)는 저장하지 않습니다.
    - 하루마다 바뀌는 비밀값으로 만든 HMAC-SHA256 해시의 앞 16자만 `submit_rate` 표에 시각과 함께 둡니다.
    - 민원 행(`feedback`)과는 연결하지 않습니다.
    - 24시간이 지난 기록은 지웁니다. 지금은 **다음 접수가 들어올 때** 지우므로, 접수가 끊기면 오래된 기록이 잠시 남을 수 있습니다(보완 예정).
    - local 서버의 비밀값은 메모리에만 있어 날짜가 바뀌거나 서버를 다시 켜면 새로 만들어집니다.
    - Supabase에서는 운영자 코드 해시와 날짜를 키로 씁니다.
  - **구역 몰림 표시:** 한 구역에 웹 접수가 **1분 20건 이상** 들어오면 막지 않고 관제에 몰림 표시만 합니다. 심각도 계산은 그대로입니다.
  - 켜고 끄기: 환경변수 `DEDUP_ENABLED=0`(합치기), `SUBMIT_LIMIT_ENABLED=0`(폭주 거절).
  - Supabase에서는 폭주 거절이 `x-forwarded-for` 헤더에 의존합니다. 실제 접속자 주소가 오는지 확인이 남아 있습니다(할일 D5-33 [참모 · 구현 검토]).
- 심각도 판정은 AI가 아니라 고정된 계산식이 수행합니다. 같은 입력에 항상 같은 결과가
  나오며 근거를 화면에 표시할 수 있습니다.

이 시스템은 조치의 우선순위를 제안합니다. 최종 판단과 조치 책임은 운영 담당자에게
있습니다.
